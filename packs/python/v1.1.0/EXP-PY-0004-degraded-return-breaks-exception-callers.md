## 详细描述

在一次「公共请求层收口」的改动中，公共请求函数被从「解析失败时抛异常」改为「返回一个降级结构」——失败不再抛出，而是返回形状完好的空字典或 `None`。改动本身只动了公共层的一个判定分支，看起来是收敛行为、减少崩溃。

实测结果是三处既有调用方的行为同时反转：

1. **持仓查询函数**把查询失败报成 `ok=True, size=0`。上游消费方看到 `ok=True` 就计入「查询成功」的计数，于是把「这次没读到」读成「已确认没有持仓」—— 这是一个语义完全不同的结论，且方向上偏危险（把未知当成已知的空）。
2. **行情订阅类函数**在失败时返回 `None`，直接违反其声明的 `-> dict` 返回类型；调用方在 `None` 上做键访问，错误被推迟到离故障点更远的地方才爆发。
3. **一键平仓入口**（`<module>` 中的下单封装）把失败静默报成「平仓成功」—— 最危险的一处：用户得到的是一个假的成功确认。

三处调用方**都不是本次新写的代码，但让它们失效的新入口（降级返回值）是本次引入的**。这正是问题的关键：一次改动的爆炸半径由「谁依赖旧行为」决定，而当依赖旧行为的方式是异常传播时，这个集合在源码里没有任何符号可搜。

## 根因链

1. **现象层**：三处调用方把「失败」读成「成功 / 空」，且症状与真正的业务失败逐字相同（同样的成功路径、同样的日志），无法从输出侧区分。
2. **直接原因**：公共请求层从「失败抛出」改为「失败返回降级结构」，判定分支被改掉。
3. **为什么漏掉清点**：依赖旧行为的方式是**隐式**判据 —— 调用点靠 `try/except` 的传播来判定失败，`grep` 函数名能找到调用点，但 grep 不出「这个调用点是否依赖异常」；收口时只检查了公共层内部，没有反向清点依赖方。
4. **本质原因**：异常是控制流契约，不是数据契约。它不在类型签名里、不在返回结构里，因此静态工具全盲。改「抛异常」为「返回哨兵」，在类型层面可以是零 diff，这让「改了一个函数」和「改了 N 个调用点的控制流」在评审材料上看起来完全一样。

## 代码示例

### ❌ 错误示例

```python
# 公共请求层：失败时不再抛出，改返回「形状正常」的降级结构
def request(path: str, params: dict | None = None) -> dict:
    try:
        resp = client.get(path, params=params)
        return resp.json()
    except Exception:
        # ❌ 哨兵值 200 落在成功白名单里；调用方无法与真实成功区分
        return {"code": 200, "data": {}}


# 调用方：只靠异常判定失败 —— 现在这条 except 永远不会触发
def query_position(symbol: str) -> dict:
    try:
        data = request("/position", {"symbol": symbol})
    except Exception:
        return {"ok": False, "size": 0}
    # ❌ 失败也走到这里 → ok=True, size=0，被上游读成「已确认无仓」
    return {"ok": True, "size": data.get("data", {}).get("size", 0)}
```

### ✅ 正确示例

```python
# 失败哨兵明确避开整个成功白名单
SENTINEL_FAILED = -1
SUCCESS_CODES: frozenset[int] = frozenset({0})   # 统一白名单常量，禁止各处内联


def request(path: str, params: dict | None = None) -> dict:
    resp = client.get(path, params=params)
    if not (200 <= resp.status_code < 300):
        return {"code": SENTINEL_FAILED, "data": None}   # 与成功值域不相交
    return resp.json()


# 调用方：不靠异常传播，靠统一白名单常量判 code
def query_position(symbol: str) -> dict:
    data = request("/position", {"symbol": symbol})
    if data["code"] not in SUCCESS_CODES:
        return {"ok": False, "size": None}   # 显式失败，不伪装成「空仓」
    size = data["data"]["size"]
    return {"ok": True, "size": size}


# 反向对照：真的为空时，仍必须报成功（防矫枉过正）
def test_empty_position_reports_success():
    result = query_position("SOME_SYMBOL")   # 桩：code=0, size=0
    assert result == {"ok": True, "size": 0}
```

## 对应失败模式

**(k) 契约断层（contract_gap）**：公共层的返回契约从「失败即抛出」变成「失败返回降级结构」，而下游调用方仍按旧契约（异常传播）判定成败。接口两侧对「成功」的定义不再一致：提供方认为「返回了结构就是成功」，消费方等待一个永不到来的异常，于是把失败态当成正常态消费。这正是契约断层的定义 —— 契约变了、消费方没跟着变，且变化在类型层面不可见。

**置信度说明**：0.85。源记录有实测证据（三处调用方行为反转，且逐点列出了各自的反转形态），不是推测；修复模板包含「哨兵值必须避开整个成功白名单」这一可判定的设计约束，能直接落成用例。未给更高分是因为证据来自单次改动（`occurrences: 1`），样本面窄，且三处反转的具体下游影响面（有多少上游消费方）未量化。

## 改进方向

- **短期**：改动任何「抛异常 → 返回哨兵 / 降级结构」的公共函数前，必须先列出全部调用点，并逐点标注判据（显式判 code / 靠异常 / 靠冻结形状）；把靠异常的几处改为对统一白名单常量判 code，禁止各处内联业务成功码。
- **短期**：哨兵值必须避开整个成功白名单（用 `-1` 而不是 HTTP 状态码 `200`）；每处调用点补一条「真的为空仍报成功」的反向对照用例。
- **长期**：把「异常传播」这类隐式契约显式化 —— 凡是改动异常行为（新增/移除/替换抛出点）的提交，变更描述必须附带调用点清点结果，评审时按控制流变更而非数据变更对待。
- **长期**：成功判定收口到单一常量表，并用静态检查禁止在业务分支里内联成功码字面量。
