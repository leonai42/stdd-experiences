## 详细描述

备份文件名由**秒级**时间戳构成。触发覆盖的不是「用户手动连续备份两次」这种低频操作，而是流程的固定步骤：回滚流程会先自动再备份一次当前状态，当这一步与首次备份落在同一秒时，两次备份生成的文件名完全相同，而备份函数用的是写覆盖语义 —— 首个备份被静默删掉。

于是回滚时出现三个症状：

1. **回滚后数据未恢复到备份点**：恢复源已不是用户以为的那个备份。
2. **备份目录 glob 数量少于预期**：少的那一个正是被覆盖的首个备份。
3. **备份文件内容包含备份之后插入的记录**：这是最能定性的一条 —— 恢复源里出现了本不该存在的数据，直接证明它已被「回滚前那一刻的状态」污染。

三个症状都是**静默**的：没有异常、没有告警、没有日志，唯一的信号是文件数量比预期少一个。而这类损失只在下次恢复时才暴露，此时原始数据往往已经不可再生。

## 根因链

1. **现象层**：回滚未回到备份点，且备份文件内容包含备份后的记录。
2. **直接原因**：备份文件名只精确到秒，同秒两次备份同名；备份写入使用覆盖语义。
3. **为什么必然被触发**：回滚流程**内部**自己会再备份一次，因此「同秒两次备份」不是偶发时序巧合，而是流程在秒内跑完时的默认结果。触发条件由流程结构决定，不由使用者行为决定。
4. **为什么静态看不出来**：备份代码本身是正确的 —— 它确实在每次调用时都生成了一个文件；覆盖发生在文件系统的同名语义里，不在代码逻辑里。评审代码时看到的是「每次都备份」，实际行为是「同秒只留最后一个」。
5. **本质原因**：**用时间戳承担唯一性**。时间戳给出的是「概率唯一」，而备份点可寻回是必须「保证唯一」的不变量。二者不匹配时，破坏只发生在时间分辨率之内的重复上 —— 也就是最不容易在测试中偶然撞到的那一档。

## 代码示例

### ❌ 错误示例

```python
def backup(db_path: Path, backup_dir: Path) -> Path:
    # ❌ 秒级时间戳：同一秒内两次备份 → 同名 → 后者覆盖前者
    stamp = datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%S")
    dest = backup_dir / f"{db_path.stem}.{stamp}.bak"
    shutil.copy(db_path, dest)   # ❌ 写覆盖语义，旧备份静默消失
    return dest


def rollback(db_path: Path, backup_dir: Path, point: Path) -> None:
    backup(db_path, backup_dir)   # ❌ 回滚流程内部自动再备份一次
    restore(db_path, point)       # 若与首次备份同秒 → 恢复源已被覆盖
```

### ✅ 正确示例

```python
def backup(db_path: Path, backup_dir: Path) -> Path:
    # ✅ 微秒 + uuid 片段：唯一性不再依赖时间分辨率
    stamp = datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%SZ%f")
    dest = backup_dir / f"{db_path.stem}.{stamp}.{uuid4().hex[:8]}.bak"
    # ✅ 唯一创建语义：目标已存在就报错，而不是覆盖
    with open(dest, "xb") as dst, open(db_path, "rb") as src:
        shutil.copyfileobj(src, dst)
    return dest


def test_backup_files_are_unique(tmp_path, db_path):
    first = backup(db_path, tmp_path)
    second = backup(db_path, tmp_path)        # 同一秒内连做两次
    assert first != second                    # ✅ 文件名不同
    assert len(list(tmp_path.glob("*.bak"))) == 2   # ✅ 备份目录文件数符合预期
```

## 对应失败模式

**(f) 运行时偏离（runtime_deviation）**：预期行为（回滚后数据恢复到备份点、每个备份都留档）与运行时实际行为（恢复源被同秒后写覆盖、备份文件数少于预期）不一致。偏离不来自备份逻辑本身 —— 它在代码层面始终「正确执行」，而来自文件名唯一性的实现选择，因此在阅读代码时不可见，只在运行时暴露。

**置信度说明**：0.85。时间戳精度导致的覆盖是可确定性复现的（同秒两次备份必然同名），不依赖概率或环境；修复模板（`%f` 微秒或 uuid 片段）直接可用，且不改变接口形状，落地成本低。未给更高分是因为 `occurrences: 1`，且触发需要「两次备份落在同一秒」这一时序条件，在更慢的机器或更大的库上未必每次都命中。

## 改进方向

- **短期**：备份文件名时间戳加微秒（`%Y%m%dT%H%M%SZ%f`）或追加 uuid 片段；备份写入改用唯一创建语义（`open(dest, "xb")`），目标已存在时直接报错而不是覆盖。
- **短期**：测试断言备份目录的文件数（同一秒内连做两次备份 → 文件数 +2），把「备份点必须可寻回」变成可执行的断言。
- **长期**：凡是需要唯一标识的地方，都不让时间戳单独承担唯一性；唯一性下沉到文件系统（唯一创建）或使用显式 uuid。
- **长期**：恢复类操作在开始前校验恢复源的存在性与新鲜度，把「恢复源未被污染」作为流程前置不变量检查，而不是事后才发现。
