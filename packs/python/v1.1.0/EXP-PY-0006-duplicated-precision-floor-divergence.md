## 详细描述

一张共享的精度表（记录最小变动单位、精度位数等）被两处代码各自实现了一遍消费逻辑：

- **价格引擎**里的对齐辅助函数带 `+1e-9` 的 epsilon，用于吸收浮点表示误差；
- **客户端下单函数**内联的另一份对齐逻辑不带 epsilon。

在绝大多数取值上两者结果相同，所以在近整数乘积上才暴露分歧：

```
0.29 × 100 = 28.999999999999996
  带 epsilon：floor(28.999999999999996 + 1e-9) = 29  → 0.29   （本地记录）
  不带：      floor(28.999999999999996)        = 28  → 0.28   （对方实收）
```

结果是本地记 0.29、对方实收 0.28，**多截了一个最小变动单位**。这不是舍入方向的错误，而是「同一份契约存在两个实现」的必然结果：只要两份实现在某个输入上不等价，就一定会有一条路径给出与契约本意不符的值，而这条路径是随机决定的（取决于哪一处被调用）。

问题的引爆点是「放宽 / 修改共享常量表的取值」这类看似安全的操作：表变了，两条路径同时跟着变，但只有一条有测试覆盖。评测时看到的全绿，只证明了被覆盖的那一条路径仍然正确。

## 根因链

1. **现象层**：本地记录的成交价与对方实收价差一个最小变动单位，且只在近整数乘积上出现。
2. **直接原因**：两处 floor 实现不一致 —— 一处用 epsilon 吸收浮点误差，一处直接截断。
3. **为什么会有两份实现**：精度对齐是一段「短、看起来显然、到处都要用」的逻辑，最容易被复制而不是抽出来共享；复制时又只带走了自己当时需要的那部分（epsilon 就在这一步掉了）。
4. **为什么放宽表取值会引爆它**：`「表是唯一来源」这个结论只对数据成立，对消费数据的代码路径不成立`。改表的人按「单一数据源」的心智模型评估影响面，而实际影响面是「表的消费者集合 × 每个消费者的实现是否等价」。前者可以用 grep 表名得到，后者只能用 grep **字段名** 并逐个核对算法，两者差着一个量级。
5. **本质原因**：契约的载体被误认为只有数据（表），而真正的契约是「表 + 消费它的代码路径」。当同一个数据源存在多份实现时，契约在实现层面已经分裂，但任何只看数据源的工具都发现不了。

## 代码示例

### ❌ 错误示例

```python
TICK_SIZE = 0.01   # 共享精度表的取值之一


# ❌ 实现 A：价格引擎内的对齐辅助函数（带 epsilon）
def align_price_engine(value: float) -> float:
    return math.floor(value / TICK_SIZE + 1e-9) * TICK_SIZE


# ❌ 实现 B：客户端下单函数内联的一份（不带 epsilon）
def align_order_price(value: float) -> float:
    return math.floor(value / TICK_SIZE) * TICK_SIZE


align_price_engine(0.29)   # → 0.29   （+1e-9 把 28.999999999999996 抬到 29）
align_order_price(0.29)    # → 0.28   （直接截断 → 与本地记录差一个最小变动单位）
```

### ✅ 正确示例

```python
TICK_SIZE = 0.01

# ✅ 唯一实现：所有消费者都调用它，禁止各自保留副本
def align_to_tick(value: float) -> float:
    _EPS = 1e-9   # 吸收浮点表示误差，避免 0.29 被截成 0.28
    return math.floor(value / TICK_SIZE + _EPS) * TICK_SIZE


# ✅ 差分断言：任何消费者与主实现必须「同一输入 → 同一输出」
@pytest.mark.parametrize("value", [0.29, 0.3, 1.0, 28.999999999999996 / 100])
def test_consumers_agree_with_primary(value):
    assert align_order_price(value) == align_to_tick(value)


# ✅ 判别性测试：在提交边界捕获真正下发的参数，而不是只断言本地值
def test_order_params_carry_aligned_price(fake_client):
    place_order(symbol="SOME_SYMBOL", price=0.29)
    assert fake_client.last_params[ORDER_PRICE_FIELD] == 0.29   # 不是 0.28
```

## 对应失败模式

**(k) 契约断层（contract_gap）**：契约的「数据源」是单一的（一张精度表），但契约的「实现」有两份，且两份在近整数输入上不等价。于是同一次业务动作在本地记录与对方实收之间产生了系统性偏差 —— 接口两侧看到的是同一个契约，执行的是两套语义。这属于契约断层在「实现侧」的形态：不是接口签名对不上，而是接口背后的取值语义对不上。

**置信度说明**：0.85。有具体可复算的数值分歧（`0.29×100 = 28.999999999999996`，两处 floor 的差异可逐位验证），并且给出了可复用的「grep 字段名找消费者」方法，他人可照做复现。未给更高分是因为本次只观测到 2 个消费者命中（`occurrences: 1`），无法说明该模式在更大代码库中的检出率。

## 改进方向

- **短期**：修改任何共享常量表的取值前，先 `grep` 表的**字段名**（而不只是表名）找齐全部消费者，本次实测命中 2 个源文件；对每个消费者追问「它有测试覆盖吗？算法与主实现一致吗？」。
- **短期**：为每个消费者与主实现之间加差分断言（同一输入 → 同一输出）；在提交边界加 mock 判别性测试，捕获真正下发的参数（订单数量 / 价格字段），而不是只断言本地计算结果。
- **长期**：让两处实现共享同一个 helper，禁止各自保留副本；把「精度对齐」这类短小通用的逻辑纳入「抽 helper 而非复制」的强制清单。
- **长期**：在评审清单中把「共享常量」的影响面定义从「数据」修正为「数据 + 消费路径」，凡是改共享表取值的提交都必须附消费者清点结果。
