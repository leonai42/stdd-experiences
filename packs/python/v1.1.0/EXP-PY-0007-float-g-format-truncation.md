## 详细描述

对方系统要求的参数是**整数值字符串**（`2.0` → `"2"`），但本地可配区间是连续的 `[1.0, 5.0]`。这两个前提叠加，意味着格式化函数必须在两个分支上都精确：

- 整数分支：必须去掉 `.0`，输出 `"2"` 而不是 `"2.0"`；
- 非整数分支：**不许取整**，必须原样保留。

实现选择了 `f"{x:g}"`。`g` 格式按「有效数字」而非「小数位」工作，默认只有 **6 位有效数字**，于是：

```
f"{1.9999999:g}"  →  "2"
f"{2.0000004:g}"  →  "2"
```

两个不同的近整数取值塌缩成同一个字符串。源记录特别指出其中**向上**的那一侧最危险：`1.9999999` 被抬成 `2`，**凭空放大名义敞口**；而且这个结果是形状完好的整数字符串，会顺利通过「值是整数」之类的格式校验，失败因此**伪装成成功**。

也就是说，这不是「精度不够导致多一点小数」这种可容忍的失真，而是**语义被改变**：调用方填的是 1.9999999，对方系统收到并执行的是 2。

## 根因链

1. **现象层**：近整数的连续取值被下发成同一个整数字符串，无任何告警，校验通过。
2. **直接原因**：`:g` 的精度上限是 6 位有效数字，与「非整数原样保留」的需求不匹配。
3. **为什么选错**：选型依据是一个**直觉假设** ——「`:g` 对非整数原样保留」。这个假设没有被验证过，而它恰好写在设计文档里，于是文档为错误选型提供了「合法依据」。
4. **为什么没被测出来**：区间校验只查**范围**（是否落在 `[1.0, 5.0]`），不查**精度**；测试用例通常使用 1.0 / 2.0 / 2.5 这类「整齐」取值，它们在 `:g` 下恰好正确。只有近整数取值（1.9999999、2.0000004、5.0000001）才会暴露，而这些取值在正常使用中极少被主动输入。
5. **本质原因**：**规格声明与实现能力分叉**。文档承诺的是「保真」，实现提供的是「6 位有效数字内的保真」。运行时行为与 spec 不一致，但两者都被认为是正确的，因为没有人把 spec 那句话当作可验证的断言去测。

## 代码示例

### ❌ 错误示例

```python
def format_param(value: float) -> str:
    # ❌ :g 默认 6 位有效数字，近整数取值会被静默舍入成整数
    return f"{value:g}"


format_param(2.0)        # → "2"    （看起来正确，遮蔽了问题）
format_param(1.9999999)  # → "2"    ❌ 向上放大名义敞口
format_param(2.0000004)  # → "2"
format_param(5.0000001)  # → "5"
```

### ✅ 正确示例

```python
def format_param(value: float) -> str:
    if value.is_integer():
        return str(int(value))   # 整数分支：去掉 .0，满足对方「整数值字符串」契约
    return repr(value)           # 非整数分支：float 的往返表示，不失真


format_param(2.0)        # → "2"
format_param(1.9999999)  # → "1.9999999"   ✅ 原样下发
format_param(2.0000004)  # → "2.0000004"   ✅
format_param(5.0000001)  # → "5.0000001"   ✅


# 用例固化近整数取值，断言原样下发
@pytest.mark.parametrize("value,expected", [
    (1.9999999, "1.9999999"),
    (2.0000004, "2.0000004"),
    (5.0000001, "5.0000001"),
    (2.0,       "2"),
])
def test_format_param_preserves_near_integers(value, expected):
    assert format_param(value) == expected


# 变异实测：把实现换回 :g 之后，上面这条用例必须变红
```

## 对应失败模式

**(f) 运行时偏离（runtime_deviation）**：规格（设计文档）声明「非整数原样保留」，运行时实际行为是「按 6 位有效数字舍入」。两者在日常取值上一致、在近整数取值上分叉，偏离被「格式看起来正确」掩盖 —— 典型的运行时行为与 spec 不一致，且偏离只在一个很窄的输入域上显现。

**置信度说明**：0.80。`g` 格式的有效数字上限是 Python 的确定性行为，任何人可用一行 REPL 复核，判定无歧义；修复模板还包含「变异实测」这一可执行的验证手段。未给更高分是因为 `occurrences: 1`，且该偏离对实际业务的影响（放大后的名义敞口是否真的被执行）在源记录中没有单独量化。

## 改进方向

- **短期**：把「输出给外部的数值格式化」按分支写清楚 —— 整数值走 `int()`，非整数走 `repr()`；禁用 `:g` / `:e` / `round()` 作为对外下发路径的格式化手段。
- **短期**：用例固化若干近整数取值（1.9999999 / 2.0000004 / 5.0000001）并断言**原样下发**；做一次变异实测：把实现换回 `:g`，用例必须变红 —— 用例不变红说明它没有真正覆盖这个偏离。
- **长期**：把区间校验从「只查范围」扩展为「范围 + 精度」；对可连续输入的运行时配置，校验其格式化后的往返一致性（`parse(format(x)) == x`）。
- **长期**：设计文档里凡是出现「原样保留」「不失真」这类绝对化措辞的地方，都补一条可验证的断言，否则它只是假设而非规格。
