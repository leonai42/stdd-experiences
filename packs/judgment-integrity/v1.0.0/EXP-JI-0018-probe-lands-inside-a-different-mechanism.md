## 详细描述

一次误判的形状：把「命令弹出确认框」直接读成「授权未载入」，进而建议重启会话。真实
根因落在另一套机制上 —— 读取边界会把**解析器无法静态分析**的命令一律转人工：花括号
与引号的组合、`sed` 脚本、`find -exec`、复杂管道。这与授权是否生效毫无关系。

误判的代价不是「多弹了一次框」，而是**结论指向了错误的机制**：按「重启会话」去处置，
重启后现象不变（因为命令形状没变），于是又会推给环境或权限配置，继续在错误的面上排查。
「重启无益」本身就是一条证据 —— 它说明原来的归因不成立。

判别法很便宜：换一条**裸单命令**（无引号、无花括号、无管道）复测同一件事。若它不弹框，
授权就是生效的，之前弹框的是读取边界。另一个同向信号是拦截理由文本：出现「无法静态
分析」「读取边界」之类字样时，与授权无关。

通用形态：**探针自身的形状落在了另一套机制的作用域里，于是测到的是那套机制的行为，
结论却写成了被测的机制。** 任何探针在写下结论前都要先问一句：它会不会先被别的机制
拦下？

## 根因链

1. **现象层**：命令执行前被拦，弹框确认。
2. **直接原因**：把「被拦」这一个观测结果，直接等同于「授权未载入」这一个结论 ——
   中间缺一步「拦截理由是什么」。
3. **为什么会出现**：探针用了复杂复合命令的形状，而这种形状恰好会被全局读取边界接管。
   探针与它要测的机制没有解耦：被测对象是会话授权，探针的形状却落在读取边界的判定域内。
4. **为什么这个错误的因果解释还能自洽**：两套机制在观测面上同形 —— 都表现为「执行前被
   拦一次」。同一个症状对应两条成因时，最先想到的那条（授权未载入）会挤掉另一条
   （读取边界），因为前者更贴近问题域。于是没有任何东西提示「先分辨是哪种拦截」。
5. **本质原因**：**观测点与结论不同源**。判据观测到的是「有没有被拦、理由文本是什么」，
   结论却是「授权状态如何」；若理由文本不参与判断，这个结论就只能靠猜。修正方式不是
   更小心地推理，而是让探针的形状回到最小可分析形态 —— 让探针不再被无关机制接管。

## 代码示例

### ❌ 错误示例

```bash
# canary：用复杂复合命令去测「授权是否生效」
bash -c "{ cat '<project>/<file>'; } | sed -n '1,20p'"
# → 弹框确认
# ❌ 结论写成「授权未载入」并建议重启会话 ——
#    实际是解析器无法静态分析该形状，被读取边界转人工，与授权无关
```

```text
结论栏（错误写法）：
  授权已生效？  否    ← ❌ 把「被拦」直接等同于「授权未载入」
  处置：        重启会话（重启后现象不变，于是继续在错误的面上排查）
```

### ✅ 正确示例

```bash
# ✅ canary：裸单命令，无引号 / 花括号 / 管道 —— 解析器可静态分析
<cli> status
# → 不弹框  ⇒ 授权已生效；之前弹框的是读取边界
```

```text
结论栏（正确写法：结论与根因分两栏）：
  是否被拦？    否
  根因：        授权未载入 | 读取边界      ← ✅ 二者取一，不得混写
  判别依据：    裸单命令不弹框 → 授权已生效
                复杂命令弹框 → 读取边界（与授权无关）
```

```bash
# ✅ 解析器分析不了的活：交给专用工具，或先落成脚本文件再执行
#    —— 不要在现场拼复杂复合命令

# 方式一：交给专用工具（读取 / 检索 / 匹配）
Read <project>/<file>
Grep "<pattern>" <project>/<module>

# 方式二：先落成脚本文件，再用裸命令执行
#   <project>/scripts/<task>.sh   （脚本内容随意复杂，调用侧仍是一条裸命令）
bash <project>/scripts/<task>.sh
```

## 对应失败模式

对应 `tool_misuse`（工具误用）。被误用的是**探针的形态**：命令本身合法、工具本身没错，
错在用它去测一个它在这个形状下测不到的东西 —— 探针先被另一套机制接管，结论却写成
被测机制的结论。它不是 `runtime_deviation`（不是运行时走了意外分支），也不是
`coverage_vacuum`（覆盖到了，只是测错了对象）；本质是「判据与其声称观测的对象不同源」，
由一个用错了形状的观测动作触发。

**置信度说明**：给 0.85。判别法短且可执行（裸单命令复测 + 读拦截理由文本），误判的
因果链完整（复杂命令形状 → 另一套机制接管 → 结论写成授权状态），且「重启无益」这条
本身是可复核的反证据。未给更高分是因为 `occurrences: 1`，且源记录只给出这一类命令
形状（花括号 + 引号、`sed`、`find -exec`、复杂管道）的观察，未覆盖该读取边界的完整
判定规则 —— 具体哪些形状会被转人工，需按自己环境的实际行为核实。

## 改进方向

**短期**：canary 换成裸单命令重测一次；把结论与根因分两栏写，不混为一谈。

**长期**：
- 任何探针在写下结论前先问：这个形状会不会先被别的机制拦下？把「探针形状」当作探针
  设计的一部分来评审，而不只评审它测什么。
- 遇到「被拦」时先读**拦截理由**再下结论 —— 症状相同不等于机制相同。
- 把 shell 解析不了的活固定路由到专用工具或脚本文件：这既是可读性问题，也是可观测性
  问题（复杂复合命令让「被谁拦下」变得不可分辨）。
