## 详细描述

当一个**指针**比它的**目标**先落地时，指针会在一段时间里指向一个不存在的名字 —— 而这段
时间里的所有检查都可以是绿的，因为检查的是指针本身（它的存在、它的哈希、它有没有被改动），
不是「它能不能被解析」。

本例的形态：撰写判据的动作时，被指向的测试文件尚未创建，于是写的是**预估**文件名；交付时
按职责把测试拆成了别的文件（单复数之差、按能力拆成导入 / 导出两个文件）。结果是首轮验收
里 **6/22** 条判据报待修订并报「适配器未执行」，而阶段划分与判据本身**都没有错** —— 错的
只是路径。

更值得注意的是冻结机制的观测面：它记录被冻结文件的**哈希**，却没有任何检查比对内容。
所以「指针没变」被自动读成了「一切照旧」。哈希能证明的东西比它看起来少得多：

- 哈希不变 ⇒ 这个指针与冻结时逐字相同；
- 哈希不变 ⇏ 指针指向的东西存在；
- 哈希不变 ⇏ 指针所指的文件内容与判据的期望一致。

于是这处漂移在两道确认门之间一直**没有信号**：两端各自都没有变化，中间那处不成立的关系
没有任何人观测。它只在首轮验收时才浮出来，而那时它已经表现为「一堆判据待修订」，看上去
像是判据写错了 —— 实际上判据一个字都没错。

## 根因链

1. **现象层**：首轮验收报 6/22 条待修订 + 适配器未执行，失败项集中在少数判据上；逐条看是
   动作里的路径在磁盘上不存在。
2. **直接原因**：指针写的是预估文件名，而交付时测试按职责被拆成了别的文件名。
3. **为什么会出现**：指针的**绑定时机**早于目标的**命名时机** —— 撰写判据时目标还不存在，
   而判据的撰写必须先于实现，这个先后顺序是流程本身决定的，不是疏忽。换句话说，这种漂移
   是流程结构自带的，只要有「先写判据后写实现」的顺序，就会有「指针先落地」的风险。
4. **为什么没被兜住**：冻结机制记了指针的哈希，却没有任何检查比对内容或校验可解析性。
   哈希把「没有改动」误当成了「关系成立」，于是中间那道最需要观测的关系成了唯一没人看的
   东西。此外，冻结校验的放行判据是「该文件被某条偏离登记的文本或受影响能力点名」，不是
   重算哈希 —— 这一点在修复时决定了解锁方式（登记偏离点名文件，而不是想办法让哈希对上）。
5. **本质原因**：**指针与其目标的生命周期不一致**。任何「先写引用、后写被引用者」的系统
   都会遇到这件事；差别只在于是否在绑定那一刻校验目标存在。默认不校验时，漂移就只能在
   消费端暴露，而那时它已经被包装成了「判据错了」这个误导性的表象。

# ✅ 结构性做法：先冻结场景与断言，指针在目标命名之后才绑定
FROZEN_SEMANTICS = ("scenario", "expect")     # 冻结面：语义


def bind_action(recipe, repo_root):
    """指针绑定：在目标已命名之后绑定，并在绑定的那一刻断言可解析。"""
    target = repo_root / recipe.file
    if not target.exists():
        raise UnresolvablePointer(f"{recipe['id']}: 指针目标不存在 {target}")
    return recipe


def test_repoint_changes_only_the_pointer(before, after):
    # ✅ 重新指向只改指针：场景与断言逐字保留
    assert before["scenario"] == after["scenario"]
    assert before["expect"] == after["expect"]
    assert (before["file"], before["selector"]) != (after["file"], after["selector"])


def test_every_frozen_pointer_resolves(frozen_records, repo_root):
    # ✅ 哈希不变 ≠ 目标存在：冻结面的检查必须包含可解析性
    missing = [r["id"] for r in frozen_records if not (repo_root / r["file"]).exists()]
    assert not missing, ("指针不可解析：", missing)

修复步骤的顺序也很关键：**重新指向只改指针、不动场景与断言**（漂移只在路径，判据的语义
一个字都不该动）；随后登记一条偏离并点名该规格文件 —— 冻结校验的放行判据是「该文件被某条
偏离登记的文本或受影响能力点名」，不是重算哈希。试图让哈希对上，方向就错了。

## 对应失败模式

**(k) 契约断层（contract_gap）**：断裂的是「判据声明的目标」与「实际交付的产物」之间的
契约 —— 指针的哈希被冻结保护着，而它所指向的目标在冻结时还不存在，两侧的生命周期不一致。
不归 `pipeline_break`，是因为这里并没有引用链真的断掉（文件最终都存在，只是名字不同），
断的是「指针 ↔ 目标」这层约定在冻结时刻无法成立；也不归 `coverage_vacuum`：判据数量与
覆盖并不少，少的是对指针可解析性的校验。

**置信度说明**：给 0.85。失效机制清晰且结构性（指针先落地、目标后命名，这个顺序由流程
决定而非疏忽），修复方向明确到可以逐条执行（重新指向真实存在的测试、只改指针、登记偏离
点名文件），触发信号也是可执行的（路径在磁盘上不存在、适配器未执行计数 N>0、对齐数少于
场景总数）。未给更高分有两个原因：一是源记录只记 1 次；二是源记录未给出「适配器未执行」
的具体计数（只记了「6/22 条报待修订」，故正文只用 6/22），也未记录重新指向之后是否复跑
验证 —— 即该修法在本例中**未经闭环验证**，属源记录未覆盖的部分。

## 改进方向

**短期**：
- 首轮之后逐条把动作重新指向交付时真实存在的测试，用 `-k` 选到具体用例而不是整文件跑；
  同批改正陈旧的基线数字。
- 重新指向时严格只改指针：场景与断言逐字保留，避免把「路径漂移」误修成「语义变更」。
- 登记偏离并点名该规格文件以放行冻结校验；不要试图通过重算哈希来通过 —— 哈希对不上不是
  问题的本质。

**长期**：
- **延迟绑定**：把判据拆成「冻结的语义」与「后绑定的指针」两部分，指针在目标已命名之后
  才绑定，并在绑定的那一刻断言目标存在。这样漂移在产生的那一步就报错，而不是等到首轮
  验收。
- 冻结校验的观测面从「哈希是否变化」扩展到「指针是否可解析、内容是否与期望一致」——
  哈希只能证明没被改过，证明不了关系成立。
- 把「先写引用、后写被引用者」当成一类结构性风险登记下来：凡是流程要求先写引用后写目标
  的地方，都要在绑定点补一次存在性校验。
