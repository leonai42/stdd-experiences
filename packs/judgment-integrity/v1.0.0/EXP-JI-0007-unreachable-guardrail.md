## 详细描述

「护栏是否正确」与「护栏是否可达」是两个独立属性，而绝大多数验证手段只覆盖前者。
一条判据可以逻辑完全正确、命名完全合理、注释写得清清楚楚，却**没有任何输入能让它
走到失败分支**：判据的取值域里没有调用侧比较的那个值，或者它读的指标键恒为空，或者
整块声明没有任何读取方。此时它仍然会被展示在清单里、出现在报表上、被读者当成已经
生效的保障。

源记录在同一个变更里遇到**两次**这一形态，且两次**不在同一层**：

- **代码里的 return 分支不可达。** 一个预算判据读取的指标键写在状态文件的另一层，
  读到的一直是空值，于是「预算用尽 → 回退人工」这条分支是死代码；同一处，一个范围
  判据只返回三种取值，**从不返回失败**，于是调用侧比较该失败值的分支、以及基于范围
  标记的降级规则，双双不可达。
- **配置里的声明不可达（复发 2）。** 一个声明块共 15 个键，声明各模式的阶段行为，
  其中某模式一条写着「确认门自动放行」。实测该块键名对工具链源码全仓扫描 **0 命中** ——
  整块从未也不可能生效。

两次的危害方向相同且都很具体：**读者会据此跳过确认动作**。「自动放行」这条声明如果
被当真，那么本该走的确认这一步就被合法地省掉了。这正是同类纪律教训的复现路径 ——
护栏不在场时人会谨慎，护栏在场却永不触发时人会放心。

值得单独记下的是源记录自己的处置结论：**删掉一条永不成立的护栏，比留着它更安全**。
第一反应通常是「留着吧，将来也许用得上」，但一条永不触发的护栏不是备份，是伪装成
保障的空白。它不是中性的：它会占掉清单里的一个位置，让读者以为这件事已经被管住了。

## 根因链

1. **现象层**：判据函数在跑、声明在文件里、清单上有它，但没有任何输入能让它产生
   失败结论；读者据此认为该事项已被保障。
2. **直接原因（代码侧）**：判据的取值域与调用侧的期望不匹配；指标键的读取路径与
   写入路径不在同一层，读到的恒为空。
3. **直接原因（配置侧）**：声明块写进了文件，但没有任何代码读取它 —— 声明与执行
   之间根本不存在链路。
4. **为什么验证没拦住**：测试问的是「代码写对了吗」（给定输入，算出来的值对不对），
   而不可达问的是「这段代码跑得到吗」。前者对后者的答案是永远沉默的 —— 不可达的分支
   不会让任何一条测试变红，它只是从不参与。这是一个**被测对象之外**的属性，需要换
   一个提问方式才能看见。
5. **本质原因**：护栏被当作**文本**交付，而不是被当作**执行路径**交付。「写了」与
   「生效」之间隔着一条可达性证明，而流程里没有任何一步要求出示它。于是不可达的护栏
   可以长期停留，并且比空白更危险 —— 空白会被发现，伪装成保障的空白不会。

## 代码示例

### ❌ 错误示例

```python
# ① 判据的取值域里没有调用侧比较的那个值
def <scope_guard>(state) -> str:
    ...
    if <soft_signal>(state):
        return "WARN"
    if <nothing_to_check>(state):
        return "SKIP"
    return "PASS"          # ❌ 从来没有 return "FAIL"


status = <scope_guard>(state)
if status == "FAIL":                     # ❌ 不可达：取值域里没有这个值
    degrade_to_manual("scope creep")

if "fail" in <scope_guard>(state):       # ❌ 同上：这条降级规则也永不触发
    degrade_to_manual("scope creep")


# ② 指标键的读取路径与写入路径不在同一层
def <budget_guard>(state) -> str:
    left = state.get("budget")           # ❌ 该键实际写在 state["metrics"]["budget"]
    if left is None:                     # 恒为 None → 分支永远走这一条
        return "SKIP"
    return "FAIL" if left <= 0 else "PASS"   # ❌ 永远算不到
```

### ✅ 正确示例

```python
from enum import Enum


class Verdict(str, Enum):
    PASS = "PASS"
    WARN = "WARN"
    SKIP = "SKIP"
    FAIL = "FAIL"            # ✅ 取值域覆盖调用侧比较的每一个值


def <scope_guard>(state) -> Verdict:
    if <hard_violation>(state):
        return Verdict.FAIL
    if <soft_signal>(state):
        return Verdict.WARN
    if <nothing_to_check>(state):
        return Verdict.SKIP
    return Verdict.PASS


def test_fail_verdict_is_reachable():
    # ✅ 断言的是「跑得到」，不是「算得对」：构造出真的该判 FAIL 的输入
    state = make_state(<hard_violation>=True)
    assert <scope_guard>(state) is Verdict.FAIL


def <budget_guard>(state) -> Verdict:
    raw = state.get("metrics", {}).get("budget")
    if raw is None:
        return Verdict.SKIP          # ✅ 读不到就是读不到，不伪装成某个取值
    return Verdict.FAIL if raw <= 0 else Verdict.PASS


def test_every_declared_key_has_a_reader():
    # ✅ 把「不可达」本身做成判据：待查键名由扫描推导，不手抄清单
    declared = scan_declared_keys(DECLARATION_DIR)      # 从声明文件里扫出所有键名
    readers = scan_source_refs(TOOLCHAIN_DIR)           # 从工具链源码里扫出所有被引用的键名
    assert declared - readers == set(), f"零读取方的声明：{sorted(declared - readers)}"
```

## 对应失败模式

**(j) 覆盖真空（coverage_vacuum）**：这里的真空不是「没写判据」，而是「判据写了、
看起来在场，但它的取值域或读取方是空的」。判据函数自己被调用、被断言、被展示，
于是任何「判据是否存在」的检查都会通过；而它真正的作用点（失败分支、声明消费点）
没有任何执行路径能到达。不归 `contract_gap`，是因为断掉的不是两侧对同一契约的理解：
一条零读取方的声明不构成契约，它只是一段文本 —— 缺的是消费者与执行路径本身。

两次复发分别落在代码层与配置层，说明这不是某一种写法的失误，而是**护栏被当作文本
交付**这一习惯的两种表现。

**置信度说明**：给 0.90（本包最高）。理由：同一形态在同一变更内出现两次、分别落在
代码与配置两层；配置侧有实测证据（整块 15 个键，全仓扫描 0 命中）；修法具体且可执行
（穷举 return 对照 + 可达性测试 + 删并说明 + 指标键报 null + 把不可达做成扫描判据）。
扣分项有二：其一，代码侧的两处不可达（取值域缺 FAIL、指标键读错层）在源记录里是
**推断**（`provenance: ai-inferred`），未附「注入一个 FAIL 输入看分支是否触发」的
复现记录，**待复核**；其二，需求侧写着同款声明的那处文本当时未同步处置，本条要求的
「两侧同时删」只完成了一半 —— 只删实现侧，等于把不可达搬到了需求侧（源记录已把它
记为下一单待办）。

## 改进方向

**短期**：
- 穷举判据函数的每一条 `return`，与调用侧比较的每一个取值逐一对照；对不上的分支，
  要么补齐取值域，要么删掉。
- 给每个失败分支 / 降级规则补一条**能触发它**的用例（构造出让该分支成立的输入），
  而不是继续加「算得对」的用例。区分标准很简单：删掉这条用例，判据的失败分支是否
  还是从没被执行过。
- 不可达且没有严重度判据可依的分支，**删掉并说明**；不要留「将来可能用得上」的注释。
- 指标字段读不到时报 null，不要报 0 —— 0 的含义是「数了，是零」，是一个结论。
- 对声明式配置做一次零读取方扫描（键名由扫描推导，不手抄清单），并对声明自述的复核
  方法逐字执行：从它自己的文本里提取命令，真跑一遍。
- 同一声明同时写在需求侧与实现侧时，两侧一起删；只删一侧不算处置完成。

**长期**：
- 把「每个失败 / 降级分支必须有一条测试证明它可达」立为交付前的固定动作 —— 与
  「验收条目执行」同性质：它问的不是「代码写对了吗」，而是「这段代码跑得到吗」。
- 声明式配置引入「声明即被消费」的断言：一份声明若没有任何读取方，就应当在交付前
  被扫描报出，而不是等读者踩上去才发现。
- 把可达性纳入评审清单：**删掉一条永不成立的护栏比留着它更安全** —— 评审时应把
  「这条护栏上次触发是什么时候、哪条用例在证明它可达」作为固定追问。
