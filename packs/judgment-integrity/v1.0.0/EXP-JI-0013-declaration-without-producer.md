## 详细描述

一个断言要能起作用，需要三个东西同时到位：**声明**（要求什么）、**生产者**（谁来满足它）、
**配方**（怎么跑、跑哪一个）。本条目的模式是其中两处同时悬空：声明了一个标记串而无人
产出它，配方的选择器又没选中任何用例 —— 而两侧的失效互相掩护，因为谁都不会报错。

实测形态是这样的：验收运行整体报「待修订」，状态为未知，且「适配器未执行」计数 N>0 ——
本例为 **17/17** 条待修订。逐条看下去，配方的动作是「在某个文件里用选择器选中某条用例」，
而那条用例并不在被运行的文件里。手工执行该配方得到 `pytest` **rc=5**、输出含
`deselected`：**选择器一条都没选中**。这里有一个特别容易被忽略的点：rc=5 是「没有收集到
任何测试」，但它在汇总里与「跑过了」长得几乎一样 —— 只要没人区分「跳过了」与「通过了」，
一条从未执行的判据就会以绿色的形式沉淀下来。

声明侧的悬空是同一个结构的另一半：配置里写着「标准输出必须包含某标记串」，而实现里没有
任何代码发出这个串。写声明的人以为写了就会被喂，跑判据的人以为绿了就是被喂过。**两个假设
都没写下来**，所以没有任何检查能发现这段声明是孤儿 —— 声明不会失败，它只会一直不被满足。

使这一切更容易发生的是输出通道：`pytest -q` 下 `print` 不可见，标记只能走 warning 通道；
如果实现侧习惯性地用 `print` 发标记，那么即便配方选对了用例，判据依旧读不到东西 ——
又多一层「跑过了但没喂到」的掩护。

## 根因链

1. **现象层**：验收整体报待修订、状态未知、适配器未执行计数 N>0；逐条看是配方没选中用例，
   以及声明没有生产者。没有任何一处报错说「这条声明没人管」。
2. **直接原因**：配方里 `-k` 选择器与 `--` 文件路径指向的两个东西不一致（选择器点名的
   用例不在该文件里），`pytest` 因而报 rc=5；声明侧点名的标记串在实现里没有生产者。
3. **为什么会出现**：声明与生产者分处两个文件、两种语言，中间没有绑定。把声明写进配置比
   把生产者写进实现容易得多，于是最容易完成的那一半先被完成，另一半留在了「以后会有人
   接上」的状态。
4. **为什么没被兜住**：两侧各有一个未写下来的假设（写了就会被喂 / 绿了就是被喂过），而
   没有任何判据去检查「声明的生产者是否存在」「配方的选择器是否选中了东西」。缺少的正是
   那条**静态**判据：它不需要跑业务逻辑，只需要把两个名字对一遍。
5. **本质原因**：**声明与生产者之间没有绑定**。断言的有效性不来自它写得多完整，而来自
   「有没有人能证明它被满足过」。一旦这个绑定不存在，声明就退化成了注释 —— 它会被人读、
   被人相信，但不参与任何判定。

## 代码示例

### ❌ 错误示例

```python
# 声明侧（配置）：要求标准输出包含标记串 <marker_a>
# - id: <case_id>
#   action: "pytest -q <module>_other_test.py -k <case_id>"   # ❌ 选择器点名的用例不在此文件里
#   expect:
#     stdout_contains: "<marker_a>"                            # ❌ 无生产者：没有任何代码发出它
```

```python
# 实现侧：既没有生产者，也没有走对通道
def test_<criterion>():
    assert <condition>
    print("<marker_a>")     # ❌ 两处问题：pytest -q 下不可见；且本用例不在配方点名的文件里
```

```bash
$ pytest -q <module>_other_test.py -k <case_id>
# 1 deselected, no tests ran in 0.01s
$ echo $?
5                            # ❌ rc=5 = 没有收集到任何测试，却极易被当成「跑过了」
```

### ✅ 正确示例

```python
# ✅ 统一助手：标记只能走 warning 通道（pytest -q 隐藏 print）
def _evidence(marker: str) -> None:
    warnings.warn(marker, stacklevel=2)


def test_<criterion>():
    assert <condition>
    _evidence("<marker_a>")     # ✅ 在判据末尾发出标记；本文件即配方点名的那个文件
```

```python
# ✅ 静态判据一：配方的选择器与它点名的文件必须对得上
def test_recipe_selector_matches_a_real_test(recipe):
    proc = run(["pytest", "--collect-only", "-q", recipe.file, "-k", recipe.selector])
    assert proc.returncode != 5, (recipe.id, "选择器未选中任何用例（deselected）")
    assert proc.stdout.strip(), (recipe.id, "未收集到任何用例")


# ✅ 静态判据二：声明点名的标记串必须在实现里有生产者，且必须走 warning 通道
def test_declared_marker_has_a_producer(recipe):
    producer = find_marker_producer(recipe.marker)          # 只认 warnings.warn / _evidence
    assert producer is not None, f"声明了标记串但没有任何生产者：{recipe.marker}"
    assert producer.file == recipe.file, (producer.file, recipe.file)
```

两条静态判据都不需要跑业务逻辑，只把两个名字对一遍：**选择器 ↔ 文件**、**标记串 ↔ 生产者**。
它们分别补上了原缺口的两半，而且能在配方或声明被改动的那一刻就变红。

## 对应失败模式

**(k) 契约断层（contract_gap）**：断裂的是「断言声明」与「生产者实现」之间的契约 ——
声明侧以配置写下要求，实现侧以代码提供证据，两者之间没有任何绑定。写的人以为写了就会被
喂，跑的人以为跑绿就是被喂过，这两个假设都没写下来，于是没有任何检查能发现声明是孤儿。
不归 `coverage_vacuum`，因为缺口不是「没有测试」（测试是有的，还在被点名），而是**声明与
实现之间没有对应关系** —— 配方甚至没有选中它，属于典型的「检查存在 ≠ 契约存在」。

**置信度说明**：给 0.85。触发信号明确且可复现：`pytest` rc=5 与 `deselected` 是该工具的
确定行为（不是观察到的偶发现象），17/17 条待修订与状态未知来自源记录；修法三步都能直接
落地（统一 `_evidence` 助手、选择器与文件路径对齐、两条静态判据）。未给更高分有两个原因：
一是源记录只记 1 次；二是源记录给出的「适配器未执行」计数写作 **N>0，未给出具体条数**，
17/17 是待修订的条数、不是逐条成因的清单，故正文不替它填数，也不声称 17 条的成因全部相同。

## 改进方向

**短期**：
- 给每个声明了标记串的测试文件加统一助手 `_evidence(marker)`（内部走 `warnings.warn`，
  带 `stacklevel`），并在判据末尾调用；排查所有用 `print` 发标记的实现，`pytest -q` 下
  它们等于没发。
- 逐条核对配方的 `-k` 选择器与 `--` 文件路径是否指向同一条真实存在的用例；改配方后点名
  文件路径，让冻结机制放行。
- 补两条静态判据：选择器 ↔ 文件、标记串 ↔ 生产者。这两条是本模式唯一能在改动那一刻就
  报警的防线。

**长期**：
- 让**声明与生产者同源**：标记串登记在一处，由实现侧的助手自动发出，声明侧只引用该登记，
  而不是各写一遍字符串。
- 在判据的汇总视图里把「跳过 / 未执行」与「通过」分开计数并显式显示 —— rc=5 与绿在输出
  上长得一样，是本条最廉价的放大器。任何「跳过」都必须带原因与数量。
- 把「每条声明是否有人满足」纳入评审清单：凡是写下断言的地方，必须同时指出**谁**、**在
  哪个文件**、**走哪个通道**满足它。写不出这三项，这条声明就还只是注释。
