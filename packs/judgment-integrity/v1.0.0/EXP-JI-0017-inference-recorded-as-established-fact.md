## 详细描述

两类记录看起来都在回答「为什么」，但都没有观测支撑。

**一、把推断写成结论。** 一条变更记录里，「成因」栏填的是一句自洽的机制说明
（例如「配置不可解析 → 进程提前退出 → 被上层 `except` 吞掉」），而登记那一刻，
手边**只有症状**。这句话读起来与实测结论毫无区别，于是后续步骤把它当成已核实的事实，
照着它去修 —— 修完症状仍在，因为那个机制从来不存在。真实形态是另一件事
（输入缺席 + 静默 + 仍打印成功行）。

**二、从代理量反推结论。** 一个冻结校验报「被冻结的文件已修改」，据此判定「有人改了
已批准的内容」并要求登记偏离。但这个判据手边只有**哈希**（代理量），没有任何
「内容是否真的变过」的独立观测点。实测的判别信号是：该文件的 **mtime 早于冻结记录的
登记时间** —— 盘上的内容其实正是被批准的那份。把「哈希对不上」等同于「内容被改」，
会让人去追一个不存在的改动。

两者是同一条原理：**记录下来的推断必须标明是推断，直到探针证明它；探针推翻它时，
把推翻记录下来，并保留原推断可见。** 推断本身不是缺陷 —— 缺陷是它被当成事实的那一刻，
以及它因此把后续步骤引向了一个不存在的机制。

**本条的覆盖边界（重要）**：关于「哈希对不上」的成因，本条只记录源记录支持的**一种**
判别机制 —— mtime 与冻结登记时间的比对。哈希不一致的成因不止一种，其余成因
（如登记环节的读法 / 编码 / 换行差异等）在源记录中没有实测证据，**属待复核**，
本条不作断言，也不声称覆盖该问题的成因全貌。

## 根因链

1. **现象层**：按记录里的成因去做复现，构造成本极低却复现不出；或按「内容被改」去
   追查，追不到任何改动。
2. **直接原因**：记录里的「成因」栏没有区分**推断**与**实测**，两种性质共用同一个字段。
3. **为什么会出现**：登记时手边只有症状。填满「成因」栏的动机是真实的（流程要求这条
   记录完整），而一句自洽的机制说明恰好满足形式上的完整 —— 它不需要任何观测成本。
   形式完整与事实成立被混为一谈。
4. **为什么后续会被放大**：记录一旦写下，就成为下游步骤的**输入**。下游读到的是一句
   陈述句，无法区分它来自推断还是实测，于是修法照着它走。错的成因不但没被纠正，
   还获得了权威 —— 问题从「一次误判」升级成「一次按误判实施的改动」。
5. **为什么代理量那一面更隐蔽**：判据设计时就只拿到了代理量。当观测面里没有与结论
   同对象的量时，「从代理量反推结论」是唯一可走的路径 —— 这不是谁偷懒，而是
   **判据的结构决定了它只能说这么满**。问题出在结论的措辞超出了观测面。
6. **本质原因**：**记录本该写「当前知道什么」，却写成了「事情是什么」。** 一份记录要能
   承载不确定性（推断 / 待复核 / 已实测），才不会把后续步骤引向不存在的机制。

### ✅ 正确示例

```python
# <module>/ledger.py

def register_change(symptom, ledger):
    ledger.append({
        "id": next_id(),
        "symptom": symptom,
        "cause": "配置不可解析 -> 进程提前退出 -> 被上层 except 吞掉",
        "cause_kind": "inference",   # ✅ 未实测前不写 verified
        "probe": None,               # ✅ 为空即「尚无探针证据」
        "overturns": [],             # ✅ 推翻记录追加在此，原推断保留
    })


def record_probe(entry, path_results, real_cause):
    """逐条路径各跑一次，记录真实触发的分支。"""
    entry["probe"] = path_results
    if real_cause != entry["cause"]:
        entry["overturns"].append({"overturned": entry["cause"], "actual": real_cause})
        entry["cause"] = real_cause        # ✅ 更新结论，但原推断仍留在 overturns 里可见
    entry["cause_kind"] = "verified"       # ✅ 有了探针证据才升级
```

```python
# <module>/freeze_check.py

def check_frozen(path, recorded_hash, current_hash, recorded_at, mtime):
    if current_hash == recorded_hash:
        return None
    # ✅ 补一个独立观测点：内容改没改，用 mtime 与冻结登记时间比对来判
    if mtime < recorded_at:
        return Deviation(path=path, verdict="hash_record_deviation")  # 内容未变，属记录环节
    return Deviation(path=path, verdict="content_drift")              # 才是真正的内容漂移
```

判别法：把 ✅ 里的 `mtime` 比对去掉、只留哈希比较，就退化成 ❌ 那一版 —— 一有哈希
不一致就必然说成「内容被改」。

## 对应失败模式

对应 `hallucination`（幻觉行为）。这里的「幻觉」不是编造 API，而是**编造因果**：
一个没有观测支撑的机制说明被当成事实写进记录，并在下游以事实的身份被消费。归
`hallucination` 而不归 `content_quality` 或 `instruction_decay`，因为核心不是格式或遗忘，
而是**声称了一件没有证据的事**；代理量那一面则表现为「结论的措辞超出了判据的观测面」。

**置信度说明**：给 0.85。两个面来自两条源记录，原理同一条，触发信号与判别法都具体
（按登记的成因去构造却复现不出；哈希不一致时先比 mtime 与登记时间）。未给更高分有两个
原因：一是**覆盖面刻意收窄** —— 关于「哈希对不上」的成因，源记录只给出 mtime 与登记
时间比对这一种判别机制，其余成因（登记环节的读法 / 编码 / 换行差异等）在源记录中没有
实测证据，本条不作断言、**标记为待复核**，也不声称覆盖该问题的成因全貌（同族的其余
分支不在本次改写范围内，需合并复核后再补）；二是两条源记录各只记 1 次发生，
尚未跨项目复现。

## 改进方向

**短期**：在记录里把推断与实测分开（字段级区分）；登记时若无探针证据，成因标
`inference`；被推翻时追加推翻记录，而不是改写原文。

**长期**：
- 把「成因栏是否标注了证据等级」纳入变更评审清单 —— 形式完整的记录最容易被当成事实。
- 给每个只观测代理量（哈希 / 计数 / 长度）的判据补一个与结论同对象的观测点；补不了，
  就在结论措辞里显式降级（「哈希记录与当前不符，内容是否变更未确认」），
  不要用只有拿到完整观测才配使用的措辞。
- 处置前先做最小可复现：按登记的成因逐条路径各跑一次。**复现不出本身就是重要信息** ——
  它提示记录里的因果是推断，而不是结论。
- 待复核对齐：本节只覆盖一种判别机制，成因全貌需与同族分支合并复核后再作断言。
