## 详细描述

让一个判据失效最省力的方式，不是让它判错，而是让它**读不到东西** —— 而它把「读不到」
当成了「没有」。本条目合并两条同族实例：一条是产出侧与消费侧键名不一致，一条是跨期
两份产物用了两套状态词表。两者都**没有报错**，都给出了一个中性结论，且结论都没有引起
任何人的怀疑。

**实例一：内容全对，但对消费侧等于不存在。** 某次变更的验收对它自己恒报「无内容」，
导致后续字段写不出、流程被卡住。当时的对照面是：全部阶段已完成、全量 **991** 条测试
全绿、检查项 **0** 个失败。根因三件事各自看都「对」：

- 读取方实际读的是 `steps`；
- 另外至少一处**注释**写着消费者读的是另一个键（`contract_points`）；
- 产出阶段照那句注释写了 **9** 条声明 —— 内容全对，对消费者等于不存在。

尤为刺眼的是自查方向：**九轮自查（含 5 组变异探针）全在查「我写的代码对不对」，
没有一轮在查「我写的东西有没有人读」。** 991 条全绿在这里不是安慰，而是证据 ——
它证明的是「既有断言都通过了」，不能证明「我产出的东西有消费方」。

**实例二：词表跨期漂移，「未决」恒为 0。** 同一条产线的两份产物用了两套状态词表：
早期一份用布尔键（`resolved: true/false`），汇总后的账本用 `status: resolved|open`。
只有第一份的时候读取方是对的，所以问题一直看不出来；汇总产物一落地，读取方读的键在
每一条上都缺失，于是命令报出「未决：0 条｜证据强度：权威」—— 而账本上明明有 **3** 条
未决。危害方向恰好是致命的：下一个会话拿到的是一份看起来完全正常的简报，说「没有未决
事项」，而且标着最高证据强度。

两个实例的共同结构是：**两侧之间没有可执行断言，且空输入被降级成一个中性词。**
第一条使键名/词表漂移不会被任何运行结果暴露；第二条使「读不到」这一整类缺陷失去了
信号 —— 它不是被漏检，而是被设计成不可见。

## 根因链

1. **现象层**：消费侧输出一个中性结论（无内容 / 0 条），机制上没有任何报错、异常或日志
   级别变化。
2. **直接原因**：键名或词表不一致，读取结果为空；产出侧写的内容没有任何读取路径消费。
3. **为什么会出现**：一致性只存在于注释与人的记忆里。**一份被读错位置的注释比没有注释
   更坏** —— 它让产出侧确信自己已经对齐过，从而降低了它的自查强度。词表的情形则是两份
   schema 在不同时期各自长出来，产物换了名字，但没有人问「读取方认哪一套」。
4. **为什么没被兜住**：两侧之间没有可执行断言。回归全绿（991 条）、检查项 0 失败，
   恰恰因为那些断言都在查「我写的代码对不对」。检查存在 ≠ 契约存在：真正的契约来自
   「两侧对同一个键名有共同约定并被断言固定」，不来自「有一堆测试通过了」。
5. **本质原因**：「读不到」与「没有」在实现里是同一种状态。当空输入退化成一个中性词时，
   键名错误就永久失去了信号 —— 它不是被漏检，而是**被设计成不可见**。凡是消费方对空输入
   只有一句中性结论的地方，这个模式就会出现。

### ❌ 错误示例

```python
# 产出侧：键名取自代码里的一句注释（注释声称消费者读 contract_points）
def write_declarations(decl_path, cases):
    doc = {"cases": [
        {
            "case_id": c.id,
            # ❌ 照注释选键名；内容全对，但没有任何读取路径会读它
            "contract_points": c.points,
        }
        for c in cases
    ]}
    write_yaml(decl_path, doc)


# 消费侧：实际读的是另一个键
def load_contract_points(decl_path):
    doc = read_yaml(decl_path)
    points = []
    for case in doc.get("cases", []):
        points.extend(case.get("steps", []))    # ❌ 键名不匹配 → 恒为空列表
    return points


def summarize(decl_path):
    points = load_contract_points(decl_path)
    if not points:
        # ❌ 中性词：把「一个字段都没读到」与「确实没有内容」合并成同一句
        return "无待核对项"
    return f"{len(points)} 项待核对"
```

### ✅ 正确示例

```python
# ✅ 键名收口为单一常量，两侧共同引用；以消费侧代码为唯一事实源，注释与文档不参与
DECLARATIONS_KEY = "steps"


def load_contract_points(decl_path):
    doc = read_yaml(decl_path)
    points = []
    for case in doc.get("cases", []):
        points.extend(case.get(DECLARATIONS_KEY, []))
    if not points:
        # ✅ 空输入必须报「查过哪些位置、期望哪个键」，而不是一个中性词
        raise EmptyInputError(
            checked=[(f"cases[*].{DECLARATIONS_KEY}", decl_path)],
            expected_key=DECLARATIONS_KEY,
            hint="若确实没有内容，请显式写入空列表并把该案例标注为「无待核对项」",
        )
    return points


# ✅ 一致性断言：统计侧键无关地数实际有多少条（两套键都认），再与消费者取到的条数比对。
#    若两侧用同一个键从同一处算，断言恒真 —— 键名漂移就永远不会红。
def count_entries_key_agnostic(cases):
    keys = ("steps", "contract_points")
    return sum(1 for c in cases if any(c.get(k) for k in keys))


def test_declared_count_equals_consumed_count(decl_path):
    cases = read_yaml(decl_path)["cases"]
    assert count_entries_key_agnostic(cases) == len(load_contract_points(decl_path)), decl_path
```

```python
# ✅ 跨期词表：两套都认；两套都没有、或取值落在词表之外 → unknown 并点名该条
STATUS_VOCAB = ("resolved", "open")


def unresolved_entries(ledger):
    out = []
    for entry in ledger["adjustments"]:
        value = entry.get("status", entry.get("resolved"))
        if isinstance(value, bool):                 # 早期布尔键归一化到同一词表
            value = "resolved" if value else "open"
        if value not in STATUS_VOCAB:
            # ✅ 既不归零也不猜：点名该条（id + 原始取值），让漂移在输出里可见
            out.append((entry.get("id"), f"<unknown: {value!r}>"))
        elif value == "open":
            out.append((entry.get("id"), value))
    return out
```

两半的修法不同，是有意的：**同一字段的键名分歧要「收口 + 断言」**（收口到单一常量，
断言两侧条数相等）；**跨期词表分歧要「都认 + 指名 unknown」**（历史产物已经归档，
不可能回改，读取方必须能容忍两套词表，并且绝不把认不出降级成 0）。

## 对应失败模式

**(k) 契约断层（contract_gap）**：这里断裂的是产出侧与消费侧之间「同一个字段叫什么」
这一最基本的契约。两处各写一遍字符串、把一致性放在注释里，等于没有契约；消费侧再把空
输入降级成中性词，使断裂无法被任何运行结果暴露。不归 `coverage_vacuum`，是因为缺口不
在于「没有测试」，而在于两侧对同一份数据没有共同约定 —— 即使有测试，只要断言与消费侧
同源（用同一个键、从同一处取数）就会恒真，测试再多也照不出来。

**置信度说明**：给 0.85。两条源记录都把失效机制与触发信号写得很清楚：一条给出了
「9 条内容全对却无人读」与「991 条全绿、检查项 0 失败」的对照，另一条给出了「恒 0 且
标着权威」与「账本上 3 条未决」的对照；修法（键名收口 + 两侧条数断言 + 空输入报查过
哪里 + 词表都认且指名 unknown）都是可直接落地的。未给更高分有两个原因：一是两条源记录
各只记 1 次，本条目合并的是同一原理在两个位置上的实例，`occurrences` 未叠加（仍记 1）；
二是两条源记录都未量化「这类静默空读在仓里还有多少处」—— 其中一条明确记了自查方向从未
覆盖此面，属系统性缺口的证据，但不是计数。

## 改进方向

**短期**：
- 把每个被消费的键名收口为单一常量，由产出侧与消费侧共同引用；以**消费侧代码**为唯一
  事实源确定键名，注释与文档一律不作为依据。
- 给每一对产出/消费关系补一条断言：声明条数 == 消费者实际取到的条数；统计侧必须键无关
  地数（见上例），否则断言恒真、等于没加。
- 把消费侧的空输入处理改为报错或结构化提示，报出**查过哪些位置、期望哪个键**；同时排查
  所有「空 → 中性词」的分支，这类分支是同一个模式的温床。
- 读取跨期产物时，把「取值落在词表之外」与「两套键都没有」都判为 unknown 并点名该条，
  绝不归零。

**长期**：
- 键名与词表作为**唯一真源**登记在一处（常量 / schema 定义），两侧只引用不重写；
  新增或改名走同一次改动，不允许一侧单独演进。
- 建立判据自检的问句清单，把「我写的东西有没有人读」提到与「我写的代码对不对」同等的
  位置 —— 本条目两条实例都是在后者全绿的情况下漏过的。
- 凡「计数 / 汇总 / 权威字段」类输出，强制要求：空输入必须可区分「没有」与「没读到」，
  并在输出里带上检查位置与期望键名。这是把「读不到」从不可见状态恢复为可观测状态的
  最低成本做法。
