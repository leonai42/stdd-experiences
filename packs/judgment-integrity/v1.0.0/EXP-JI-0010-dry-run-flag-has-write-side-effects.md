## 详细描述

一个命令行工具在帮助文本里声明：某个标志表示「只预览、不实际修改文件系统」。实际
行为是：**预览已经落盘**。这不是措辞不严谨，而是契约的一侧（帮助文本）与另一侧
（写路径）之间根本没有绑定 —— 声明写在文档里，实现写在代码里，两者各自演化，没有
任何断言把它们连起来。

源记录里有**两个不同的命令行工具**，各自独立地出现了同一机制（合计 2 次），后果各
偏一面：

- **其一：预览已把活干完。** 对一个复位类子命令传预览标志后，复位动作与复位历史
  **已经写进状态文件**；随后不带该标志的真实调用反而报「没有任何可观测项被复位
  （未找到: …）」。也就是说，「先预览再决定」的评审会得到**反向结论**：预览看起来
  什么都没发生（因为它没报错），真实调用则表示无事可做 —— 使用者据此以为这项操作
  无关紧要，而事实上它在第一次调用时就已经生效。
- **其二：预览写下了伪造的批准 / 审计链。** 对一个批准类子命令传预览标志后，批准
  证据字段被写入了一个机器生成的证据串（等于伪造了审批链），并顺带生成了本该在
  真实批准后才产生的渲染产物。更糟的是后续真实调用被**幂等短路**（「已经确认」）
  挡住，于是这条伪造记录连纠正的机会都没有。

两个工具的失败面不同，原理相同：**标志只被当作语义提示，没有被当作写保护**。写路径
的入口不检查它。

第二面尤其值得单独记下：预览写的不只是业务状态，而是**证据**。业务状态写错了可以
重算，批准印记写错了会污染「谁批准了什么」这一事实本身；再叠加上「真实调用因幂等
短路无法覆盖」，错误记录就被永久固化了。预览功能最危险的失效方式不是多写了一个
文件，而是让一个从未发生过的批准看起来已经发生。

## 根因链

1. **现象层**：带预览标志的调用改了文件系统；不带标志的调用反而说无事可做。
2. **直接原因**：子命令没有实现 dry-run 分支 —— 顶层解析收下了该标志，却从不向下
   传递；写路径入口也不检查它。标志在实现里只是一个被忽略的字符串。
3. **为什么声明与实现能长期背离**：帮助文本描述的是**设计意图**（「本应只读」），
   实现提供的是能力（「实际会写」）。两者之间没有可执行断言绑定，所以背离不会以
   任何形式报出来 —— 除非有人刻意做「预览后核对副作用」这个动作。
4. **为什么没人做这个动作**：使用者相信标志名与帮助文本。可信度来自声明本身，
   而不是来自对副作用的核对；而一次「预览看起来正常」的体验，恰恰是最容易让人
   建立错误信任的体验（它没报错、没改动的迹象，一切如常）。
5. **本质原因（含后果放大）**：**「只读」是一个效果属性，不是一个标志属性**。判断
   它是否成立，只能观测副作用，不能读标志名。而一旦写路径落在审计链上，错误就不再
   可逆：幂等短路会让后续的真实动作选择「不写」，于是伪造记录被永久保留 —— 此时
   连「再用真实动作纠正一次」这条退路都没有了。

def dispatch(args):
    if args.dry_run:
        return preview(args.cmd, args)     # ✅ 预览走独立的只读路径

## 对应失败模式

**(k) 契约断层（contract_gap）**：断的是「声明的契约」与「实现」之间的一致性。契约的
一侧写在帮助文本里（只预览、不修改文件系统），另一侧写在写路径里（不检查该标志），
中间没有可执行断言 —— 于是两侧可以长期背离而无人报警。契约在这里是**对使用者**
发出的：使用者据此决定「先预览再决定」，而预览本身已经改变了状态，依据因此失效。

源记录把两条都归为工具误用（使用者误信了预览）。本包归 `contract_gap`：缺陷本体不在
使用者的选择，而在工具声明的能力与实现之间的断层 —— 使用者改用只读方式（读账本、
检索目标条目）只能绕过它，不能修复它，下一个人还会踩同一脚。也不归
`runtime_deviation`：没有哪份规格要求「预览必然只读」，是这个工具自己声明了它并不
具备的能力。

**置信度说明**：给 0.85。理由：两条源记录来自**两个不同的命令行工具**，同一机制
独立出现两次，比单条证据强；两处后果都是可直接观测的（预览后真实调用报「无事项
可复位」、状态文件出现批准印记与渲染产物）；检测方法（预览后立刻核对副作用快照）
明确、零依赖、可当场执行。扣分项有三：其一，「标志未向下传递」这一根因在源记录里
是**推断**（`provenance: ai-inferred`），未附参数解析路径的逐行定位，**待复核** ——
实际实现也可能是「传下去了但写路径没查」，两者的修法入口不同；其二，两个工具的
失败面不同（一个污染业务状态，一个污染审计链），本条把它们按同一原理合并，
`occurrences` 记为 2（两条源记录各 1 次、来自两个不同工具），但未量化任一次的实际
影响面；其三，幂等豁免的具体条件（只有带预览印记时才允许覆盖）依赖各工具自己的
印记约定，落地时需按本工具的存储结构改写。

## 改进方向

**短期**：
- 对手上工具链的每一个预览标志做一次副作用核对：预览之后比对目标文件的行数 / mtime /
  sha256，或确认目标条目仍在。这比读帮助文本可靠，也比读实现便宜。
- 在写路径入口统一守卫该标志，把写入器换成只读实现 —— 任何写入当场报错。靠每个写点
  自觉检查，等于把契约摊薄到 N 个地方，漏一处就整条失效。
- 对已被预览污染的记录单独处置：给预览印记一个显式的机器标记，让正式调用可以覆盖它。
  否则真实动作会被幂等短路挡住，错误记录永久留存。
- 遇到标志与行为不符，作为工具缺陷单独立案并记入经验库，不要静默绕过 —— 绕过只保护
  了自己这一次，下一个人还会踩。
- 需要预览时优先用只读方式（读账本文件、检索目标条目）自行推断将发生什么。

**长期**：
- 把「预览只读」变成可执行断言：预览前后状态快照相等应当是一条测试，而不是帮助文本
  里的一句话。任何「只读」「幂等」「原子」的声明都需要有一处代码或测试指向它。
- 审计链类字段（批准印记、证据串）必须区分「机器生成」与「真实动作生成」；任何预览、
  演练、回填路径都不得写入看起来像真实印记的值。
- 复核幂等设计：幂等的目的是防止重复执行，但它的副作用是**让后续的真实动作选择不写**。
  凡幂等生效的写路径，都要问一句「如果先前的写入是错的或伪造的，这条路径还能纠正它吗」。
