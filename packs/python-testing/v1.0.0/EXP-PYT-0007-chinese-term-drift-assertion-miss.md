## 详细描述

一次 attribution 输出的断言 `assert "分配效应" in result.output` 不命中，但**退出码是 0**——
CLI 正常跑完、输出结构完整，只是断言没通过。

逐字符比对后真相很清楚：实现输出的是「配置效应」，而已批准 spec 的 THEN 原文写的是「分配效应」。
两者都是通顺的中文，语义也都在同一个话题域内，所以读代码时不会觉得别扭；但断言是字面比对，
一词之差就不命中。

值得单独记下的是**误诊路径**。这个项目在 GBK 终端下运行，UTF-8 源码经 GBK 解码后本来就显示乱码，
于是"实现输出与 spec 用词不同"和"同一段文字被错误解码"在屏幕上长得一模一样。第一反应很容易
落到编码上——查 `PYTHONIOENCODING`、查管道解码、查控制台代码页——而真正的问题是术语漂移。

判定手段因此要前置：断言失败时**先做逐字符 / 码点比对**，把"是不是同一个词"这件事变成可判定的
事实。码点一列出来，`配置效应`（配=0x914d, 置=0x7f6e）与 `分配效应`（分=0x5206, 配=0x914d）
的差异无从含糊，编码这条误诊路径当场被排除。

修复方向是 Canonical-First：**以 spec 的 THEN 原文为准对齐代码输出**，而不是反过来把测试或 spec
改成实现的措辞。spec 是已批准的权威源，实现的用词不是。

## 根因链

1. **直接原因**：实现输出的中文术语与已批准 spec 的 THEN 原文不一致（配置效应 vs 分配效应）。
2. **为什么换词不会被察觉**：两个词都是通顺的中文，且在同一语义域内，读起来"意思差不多"。
   中文术语的细微差异不像英文标识符那样刺眼，写作者不会停下来核对原文。
3. **为什么断言会以这种形式暴露**：断言按字面比对，不涉及语义相似度——一词之差即不命中；
   而退出码为 0 说明程序本身没有任何异常，失败的只有"内容是否等于承诺的措辞"这一条。
4. **为什么会被误判为编码问题**：GBK 终端下 UTF-8 源码与 GBK 解码输出都呈乱码，两类问题的
   屏幕表现完全重叠；缺少逐字符 / 码点这一步，就没有东西能把它们分开。
5. **为什么缺少拦截**：没有把 spec 的 THEN 原文当作对齐基准来检查实现输出——"以 spec 为准"
   这件事只存在于口头约定，没有体现为一次逐字比对的动作。

## 代码示例

### ❌ 错误示例

```python
# 实现：按自己的措辞习惯写输出
def render_attribution(result) -> str:
    return f"配置效应: {result['config_effect']:.2%}"    # spec 的 THEN 写的是「分配效应」
```

```python
# 测试：断言按字面比对 → 不命中
def test_attribution_output(runner):
    result = runner.invoke(cli, ["attribution"])
    assert result.exit_code == 0                 # 通过：程序本身没问题
    assert "分配效应" in result.output            # 失败：实现输出「配置效应」
```

```text
误诊路径（反模式）：
  断言不命中 + 终端乱码
    → 怀疑编码：查 PYTHONIOENCODING / 管道解码 / 代码页
    → 改编码设置后乱码依旧（因为根本不是编码问题）
```

```python
# 反模式：反向改测试去迁就实现（spec 被降格）
assert "配置效应" in result.output      # ← 把权威源改成了实现的措辞
```

### ✅ 正确示例

```python
# 第一步：逐字符 / 码点比对，先排除"以为是编码问题"的误判
def test_chinese_chars_are_identical(runner):
    result = runner.invoke(cli, ["attribution"])
    expected = "分配效应"
    assert expected in result.output, [
        (ch, hex(ord(ch))) for ch in expected      # 码点一列，差异无从含糊
    ]
```

```python
# 第二步：Canonical-First —— 以 spec 中 THEN 的原文为准对齐代码输出
def render_attribution(result) -> str:
    return f"分配效应: {result['config_effect']:.2%}"   # 与 spec THEN 逐字一致
```

```text
对齐后的确认动作：
  1) 重跑该断言 → 命中
  2) 跑全量回归 → 确认无其他术语漂移（同类近义词逐条核对 spec 原文）
```

## 对应失败模式

**(k) 契约断层（contract_gap）**：已批准 spec 声明的输出措辞与实现实际输出的措辞不一致——这正是
契约断层：契约（spec 的 THEN）前后没有变，是**实现偏离了契约**，于是断言（契约的机器化表达）
不命中。它不是 `content_quality`（这里不是风格不统一的问题，而是与已批准契约不一致），也不是
`hallucination`（实现的用词并非凭空编造，只是近义替换）。修复动作也落在契约对齐：以 spec 原文
为准改实现，而不是改测试。

**不适用场景（反例）**：若 spec 只规定了语义、没有规定字面措辞（例如"输出须包含该效应的数值"），
那么用近义词不构成契约断层，此时应放宽断言（按语义或按数值断言），而不是强行锁死措辞。

**置信度说明**：0.75 —— 根因清楚，并且给出了"逐字符 / 码点比对"这一可操作、可稳定判定的事实核查
手段，能当场排除编码误诊；中文项目里这类漂移高发，通用性有支撑。未给更高分，是因为本条只有一处
现场记录（单一术语对：配置效应 / 分配效应），且"对齐后跑全量回归确认无其他漂移"这一步在源记录中
是建议动作、没有实测结果。

## 改进方向

- **短期**：中文断言失败时先做逐字符 / 码点比对再查编码；发现漂移一律以 spec 的 THEN 原文为准
  对齐实现输出，并对同类近义词逐条核对。
- **长期**：把"面向用户的固定中文术语文案"从实现里抽出来集中定义（术语表 / 文案常量），让 spec
  与实现引用同一份定义，从结构上消除"实现时换词"的空间；同时让终端编码环境标准化，减少乱码
  对真实差异的掩盖。
