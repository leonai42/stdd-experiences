## 详细描述

一次"放宽某个上限"的改动，需要补一条测试来证明放宽**已生效**。写出来的用例直接调用了配置应用函数
（`apply_*(values, ...)`），传进一个目标取值，断言它被接受。用例全绿。

问题在于：这个函数的入参是**已校验**的字典——校验发生在配置类的写入 / 加载路径里，也就是本次真正
被改动的那一层（边界校验层）。用例从下游进入，压根没经过闸门。把它放回旧判据下跑，同样通过。

于是这条用例证明的只是"下发链路是通的"，而不是"闸门开了"。它**在旧取值下同样通过**，这意味着它对
本次改动零信息。如果被当作「放宽已生效」的契约证据提交，就是**用一条无 RED 的用例为一处未验证的
改动背书**——这比"没有测试"更危险，因为它长得像证据。

区分方法很直接，而且不需要读实现：**把该层的判据临时改回旧值，再跑这条用例**。若照样通过，
它就不经过被改的那一层，不能作为契约证据。

## 根因链

1. **直接原因**：测试入口在改动层的下游，测试路径与改动路径分叉。
2. **机制层**：配置应用函数的契约是"接受已校验的输入"——校验是它的**前置条件**，不是它的职责。
   从它进入就必然绕开闸门；这不是实现缺陷，而是它的接口位置决定的。
3. **为什么会从下游入手**：下游函数的签名最"干净"（一个字典进去、一个结果出来），不需要构造配置类、
   不需要准备配置文件或环境，是**调用成本最低**的入口。写测试时的默认选择是"最方便调用"，
   而不是"离改动最近"。
4. **为什么错误不会被测试本身暴露**：它绿了，而且绿得理所当然——链路确实通。**没有 RED 的用例
   看起来和通过的有效用例完全一样**，区别只在"把它放回旧判据下会不会失败"，而这一步默认不做。
5. **为什么流程没有拦截**：补测试的动作被理解为"为改动加一条用例"，而不是"为改动加一条**能证伪
   这条改动**的用例"。缺少"这条用例在旧判据下会失败吗"这一问，就没有东西能把两类用例分开。

## 代码示例

### ❌ 错误示例

```python
class AppConfig:
    LIMITS = {"max_leverage": 3}          # 本次改动：3 → 5

    def set(self, key, value):
        if not (0 < value <= self.LIMITS[key]):     # ← 闸门在这一层
            raise ValueError(f"{key} out of bounds")
        self._values[key] = value

def apply_config(values: dict, config: AppConfig) -> None:
    """接受**已校验**的取值，仅负责下发。"""
    for k, v in values.items():
        config._values[k] = v
```

```python
# 测试从下游进入 —— 绕过了闸门，在旧判据下同样通过（无 RED）
def test_leverage_5_is_accepted(config):
    apply_config({"max_leverage": 5}, config)      # 直接写 _values，没经过 set()
    assert config._values["max_leverage"] == 5
    # 旧判据（LIMITS = 3）下这条用例照样通过 → 不证明"放宽已生效"
```

```text
证据引用（反模式）：
  「放宽已生效」的证据：test_leverage_5_is_accepted 全绿
  → 该用例不经过边界校验层，对判据取值零信息
```

### ✅ 正确示例

```python
def test_leverage_5_passes_through_gate(config):
    """从最外层进入：必须经过被改动的校验层。"""
    config.set("max_leverage", 5)          # 穿过边界校验层
    assert config.get("max_leverage") == 5
```

```python
# RED 证据：把判据临时改回旧值，这条用例必须失败
def test_leverage_5_would_fail_on_old_bound(config):
    config.LIMITS["max_leverage"] = 3      # 临时改回旧取值
    with pytest.raises(ValueError):        # 旧判据下必红 → 证明用例确实穿过该层
        config.set("max_leverage", 5)
```

```python
def test_apply_config_keeps_values(config):
    """本用例自身无 RED，是特征化测试：只覆盖下发链路的形状，
    不作为任何判据改动的契约证据。"""
    apply_config({"max_leverage": 5}, config)
    assert config.get("max_leverage") == 5
```

## 对应失败模式

**(j) 覆盖真空（coverage_vacuum）**：被改动的那一层——边界校验层——**零覆盖**。用例存在、全绿，
但它抵达的是闸门下游，改动所在的分支从未被执行，因此"放宽是否生效"这件事没有任何证据。
源记录把它记在 `contract_gap`，理由是"断言与实现之间的契约证据失效"；这里按覆盖真空归类，
因为**契约本身并没有前后不一致**（判据与实现一致地改了），失效的是**证据**：测试没有穿过那一层，
被改动层成为零覆盖无人区。这样归类也更能指向修复动作——补一条从最外层进入的用例并做出 RED。

**不适用场景（反例）**：若被测对象**就是**下游函数本身（例如本次改动在下发逻辑而非校验层），
那么从下游进入是正确的，本条不适用。判据仍然是那一问：把改动层的判据改回旧值，这条用例
该不该失败？该失败而不失败，才是本条。

**置信度说明**：0.90 —— 「把判据改回旧值跑一次」是可操作的 RED 证伪法，不依赖读实现、不依赖工具，
通用性极强；根因（下游入口签名的调用成本最低）解释了为什么这个错误会反复发生；并且给出了下游
用例的显式标注方式，避免它被继续误引为契约证据。未给更高分，是因为本条只有一个现场实例，
且"补了端到端用例后是否真的拦住过错误"没有记录。

## 改进方向

- **短期**：为「放宽 / 修改某个校验或门禁」类改动补测试时，强制回答"这条用例经过被改的那一层吗"，
  并用"把判据改回旧值"实测 RED；下游用例一律在 docstring 里标注"自身无 RED"。
- **长期**：把"RED 证据"变成契约证据的准入条件——变更记录里凡引用某条用例为证据，必须附上它在
  旧判据下的失败实测；在测试入口选择上建立默认约定（优先从最外层进入），让"最方便调用"不再
  默认等于"正确的起点"。
