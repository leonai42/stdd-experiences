## 详细描述

现场用例 `test_cli_rerun_in_the_same_second_exits_zero_twice` 的断言是："跑两次之后，
`<project>/handoff/` 下仍然只有 1 个文件"。这个结论成立的前提是——两次调用写出**同名**文件，
而文件名是按秒的时间戳派生的，所以只在两次调用落在同一个墙钟秒内才同名。

探针很直接：在两次调用之间睡 1.1 秒，就会得到两个不同的文件名，断言必红。也就是说，
这条用例测到的不是"重复运行是幂等的"，而是"这台机器跑得够快"。

它平时是绿的，因为进程内调用比真实子进程快一个量级，同一秒几乎总能命中。而检查点（CP）把同一份
文件交给**真实子进程**时，跨秒边界就是常态，于是全量 1495 条全绿的项目上，CP 报 `needs_revision`、
契约审计报 `aligned`——两个信号互相矛盾。矛盾的解释不是契约坏了，而是**这次实跑翻了**。

教训是这一句：**「1495 passed」不等于「确定性通过」**。这也是检查点必须跑真实子进程的直接证据——
进程内跑得再快，也测不出速度差异所掩盖的相位依赖。

## 根因链

1. **直接原因**：断言把"同一墙钟秒"这个偶然条件写进了结论。
2. **为什么偶然会被写进去**：文件名的时间戳精度是秒，而"重复运行只留一个文件"的心智模型是
   "后一次覆盖前一次"；两者在秒内成立，在跨秒时不成立——测试写的是心智模型，不是机制。
3. **为什么在开发机上从不暴露**：进程内调用比真实子进程快一个量级，快到来不及跨秒；测试通过与否
   取决于运行环境的速度，而不是被测行为。
4. **为什么全量绿掩盖了它**：1495 条用例一起绿给出"确定性通过"的错觉；覆盖率、用例数这些指标
   都衡量不了"结论是否依赖时间相位"，没有任何一个计数器会变小。
5. **为什么诊断会走偏**：`needs_revision` 与 `aligned` 并列出现时，直觉是去找契约或实现的差异；
   而真正的差异在两次调用之间那不到一秒的间隔里。

```python
import datetime as dt

class _FixedDatetime(dt.datetime):
    """时间源替身：把"同一秒"从偶然变成显式前提。"""
    @classmethod
    def now(cls, tz=None):
        return cls(2026, 9, 12, 10, 0, 0)

def test_cli_rerun_overwrites_within_same_second(tmp_path, monkeypatch):
    monkeypatch.setattr(handoff_module, "datetime", _FixedDatetime)
    run_cli(tmp_path)
    run_cli(tmp_path)
    assert len(list((tmp_path / "handoff").iterdir())) == 1
```

## 对应失败模式

**(j) 覆盖真空（coverage_vacuum）**：这个场景**有**一条测试，但它覆盖的不是它声称覆盖的行为——
断言命中的是"运行速度"而非"重复运行的幂等语义"，于是真正的行为分支（跨秒、两个文件）零覆盖。
这属于覆盖真空的典型形态：账面上有用例、有 1495 条全绿的记录，而实际被抵达的语义分支是空的。
它不是 `runtime_deviation`（运行时行为并不偏离 spec，spec 也没有承诺"同一秒"），也不是
`tool_misuse`（没有用错任何工具参数）——问题在"覆盖了什么"。

**不适用场景（反例）**：若被测行为本身**确实规定**了秒级时间戳语义（例如"同一秒内必须覆盖、
跨秒必须新建"），那么按秒派生命名就是契约的一部分，此时该断言成立，应改为显式注入时钟分别
断言两侧；本条不适用于这种"秒边界本身就是需求"的场景。

**置信度说明**：0.85 —— 根因清楚（文件名精度 + 进程内与子进程的速度差），并且有 1.1 秒睡眠的
最小探针可以稳定复现（必红），「CP 红 / 契约审计绿」的矛盾信号也很有辨识度。未给更高分，
是因为"1495 passed ≠ 确定性通过"这一命题虽通用，但本条只有一个现场实例，且修复后的效果
未经记录。

## 改进方向

- **短期**：对所有"目录里还剩几个文件""是否同名覆盖"这类断言做一次审查，凡结论依赖时间相位的
  一律注入时钟；同时在质量门里补一条真实子进程实跑，别只跑进程内用例。
- **长期**：把"确定性"作为与覆盖率并列的独立维度——报告里明确区分「用例通过」与「结果确定」；
  对使用时间戳、`uuid`、随机数、进程内缓存的被测边界建立默认的注入规范，让偶然条件无处藏身。
