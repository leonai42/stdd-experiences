## 详细描述

策略侧维护一个推迟/重试队列，用来暂存「本轮未能提交、下一轮应重试」的腿。这类队列的
存在本身就说明系统承认「提交可能失败」；但只要有一条代码路径**无条件**把它清空，这份
承认就被抹掉了。

实例：配对策略调仓时取价失效，导致一条腿的提交被放弃，而另一条腿已经成交。清空队列的
那条路径不读每个元素的提交结果，于是被放弃的那条腿既没有成功、也没有留在队列里等下一轮
重试 —— 它从状态里消失了。结果是单边敞口（裸暴露）一直持续到**下一轮调仓**才被顺带清理。

这里最需要看清的一点是：「队列空了」在状态上与「队列处理完了」完全相同。任何只看队列
长度、或把队列清空当作一轮结束标志的检查，都无法发现异常 —— 缺陷的整个生命周期里，
系统所有可观测的状态都是「正常」的。

## 根因链

1. **现象层**：一条腿成交、另一条腿没成交，敞口单边悬挂到下一轮调仓才被清理。系统里没有
   任何告警，因为丢弃路径不写 ERROR 日志。
2. **直接原因**：某条代码路径（新一轮开始 / 仅平仓轮）无条件把队列置为 `[]`，该路径不读
   每个元素的提交结果。
3. **为什么漏掉逐条判定**：清空方拿不到提交调用的返回值 —— 提交封装丢弃了结果，或返回的是
   状态快照而非本次调用的结果。于是「这个元素提交成功了吗」这个问题在清空点**无法被提问**，
   代码只能退化为「先把队列清掉，下一轮重来」。
4. **本质原因**：把「队列」当成了状态位（一个可重置的计数器），而它实际是**义务账本**
   （每个元素代表一笔尚未了结的配对义务）。状态位可以重置，账本只能逐条核销。一旦二者
   混淆，「重置」就等于「凭空销账」，而销掉的账在市场侧依然存在。

## 代码示例

### ❌ 错误示例

```python
def run_round(ctx):
    queue = ctx.state.get("deferred_legs", [])

    # 新一轮开始：把上一轮的推迟队列清掉，当作状态重置
    ctx.state["deferred_legs"] = []          # ❌ 无条件清空，不读任何提交结果
    logging.info("deferred queue cleared")   # ❌ 与「全部处理完成」共用同一条 INFO

    for leg in queue:
        try:
            submit(leg)                      # ❌ 返回值被丢弃
        except Exception:
            continue                         # ❌ 静默跳过，无 ERROR、无计数
    # 进入下一轮时，队列里已经什么都没有了
```

上面这段的失败模式是：`submit(leg)` 返回 `None`（未成交）与抛异常，都不影响
`ctx.state["deferred_legs"]` 的最终值 —— 它永远是 `[]`。

### ✅ 正确示例

```python
def run_round(ctx):
    queue = ctx.state.get("deferred_legs", [])

    retained = []      # identity 保留列表：只有「有成功证据」的元素才留下
    for leg in queue:
        try:
            result = submit(leg)
        except Exception as exc:
            result = None
            logging.error(
                "deferred leg submit raised: legs=%d symbol=%s attempts=%d reason=%r",
                len(leg["legs"]), leg["symbol"], leg["attempts"], exc,
            )

        if result is not None:
            retained.append(leg)            # ✅ 出队判据 = 成功完成的证据
        else:
            # ✅ 每条丢弃路径都有 ERROR，且带足定位信息
            logging.error(
                "deferred leg dropped: legs=%d symbol=%s attempts=%d reason=submit_returned_none",
                len(leg["legs"]), leg["symbol"], leg["attempts"],
            )
            if leg["attempts"] + 1 < MAX_ATTEMPTS:
                retained.append({**leg, "attempts": leg["attempts"] + 1})

    # ✅ 以保留列表整体替换，且只在此处写回一次
    ctx.state["deferred_legs"] = retained

    if queue and not retained:
        # 「清空」与「全部成功」必须是两条不同的日志
        logging.info("deferred queue drained: all %d legs submitted", len(queue))
```

注意「只在此处写回一次」这一点：如果改成在循环内逐条从原列表里 `remove`，途中抛出的
异常会让已经提交成功的元素复活（它们从未被移出），下一轮会被重复提交。

## 对应失败模式

**(k) 契约断层（contract_gap）**：队列的写入方（提交封装）与清空方对「一个元素算不算
处理完」的契约不一致。写入方知道的是「本次提交的结果」，但它不把这个结果交出去（丢弃
返回值）；清空方需要的是「每个元素是否已成功提交」，但它在清空点拿不到这个信息，只能用
「循环结束」这个与元素成败无关的信号代替。两侧对「已处理」的定义不同、且中间没有任何
一处做对齐 —— 于是队列的状态语义（空 == 全部成功）与它的真实语义（空 == 结果未知）
分裂。这不是简单的「漏了重试」：重试逻辑只要愿意就可以补上，而这里失效的是**状态本身
已经不再表达事实**，后续任何基于队列状态的判断都不可信。

**置信度说明**：给 0.90。源记录给出了完整因果链（队列清空 → 未提交元素从状态消失 →
单边裸暴露），并落到具体实例（配对策略调仓时取价失效，一条腿被丢弃、另一条腿已成交，
敞口持续到下一轮调仓才被清理），不是推测；修复模板包含一条可判定的设计约束 —— 「出队
判据必须是提交调用返回非 `None`」，可以直接落成用例。未给更高分是因为源记录只记了 1 次
发生，缺可复跑的复现证据，且「持续到下一轮调仓才被清理」的实际资金影响面未量化。

## 改进方向

**短期**：
- 立刻清点所有推迟/重试队列（以及任何「待办 + 重试」语义的容器），逐处确认「清空点是否
  读得到每个元素的处理结果」。读不到的，一律改为按元素结果逐条判定。
- 把「静默丢弃」改成硬约束：任何丢弃元素的路径必须写 ERROR，日志字段固定为
  `legs / symbol / attempts / reason`，便于事后按 symbol 聚合核对。
- 给队列元素补上 `attempts` 字段并保持元素不可变，使「重试若干次后放弃」成为一个**有日志
  的显式决策**，而不是一次静默的清空。

**长期**：
- 把「队列 = 义务账本」写进设计约定：凡表示未了结义务的容器，禁止整表重置；只能逐条
  核销，且核销必须带证据。
- 增加一条端到端不变量：**已成交腿数与未了结配对义务数之和应恒定**。这个不变量在队列被
  无条件清空时会立刻破掉，比任何单点检查都更早报警。
- 在评审清单里加一项：看到 `= []` / `clear()` / `reset()` 作用于一个承载义务的容器时，
  必须能回答「被清掉的那些元素，各自的结果是什么」。
