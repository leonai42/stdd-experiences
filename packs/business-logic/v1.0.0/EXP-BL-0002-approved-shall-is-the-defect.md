## 详细描述

实例：风控平仓轮的规格条款（已批准）要求「保留尚未成功提交的待开仓腿」，对应用例断言的
正是这个保留行为。实现忠实于 spec，测试全绿。

但这个行为本身是错的：让待开队列**活过策略自身的风控离场**，随后在策略已经离场之后又把
刚离场的一对仓位重新开出来；一旦其中只有一条腿成交，就形成单边裸暴露。也就是说，被 spec
要求「保留」的那些腿，恰恰是风控刚刚决定要离开的东西 —— 保留它们等于把风控的决定反转。

这条经验真正反直觉的地方在于：**这里的绿色是反证据**。通常「用例全绿」被当作实现正确的
证据，但在 spec 本身有缺陷、且用例断言的正是该缺陷行为时，绿得越彻底，说明实现越忠实，
缺陷被固化得越牢。测试覆盖率越高，越说明这个错误行为被牢牢锁死在系统里。

## 根因链

1. **现象层**：实现与 spec 完全一致、用例全部通过，但系统在风控离场后重新开出裸暴露仓位。
2. **直接原因**：spec 中的一条 SHALL 本身有缺陷，并且它的 TC 断言的正是这条缺陷行为。
3. **为什么流程没有阻止**：验证的对照物是 spec。当偏差同时存在于 spec 和用例中时，
   「实现 vs spec」的一致性检查恒为通过。任何只在这个层面工作的角色，无论多严格，都
   不可能发现它 —— 这不是执行力问题，是参照物问题。
4. **本质原因**：把「按规格交付」等同于「交付正确的东西」，于是没有人被授权去质疑规格。
   资金安全类需求没有一条「忠实实现的最坏后果」推演，spec 的正确性因此从未被独立检验过。
   解决方向是补一个角色和一个动作（谁来质疑、怎么质疑），而不是加更多测试。

## 代码示例

### ❌ 错误示例

```python
# spec 条款（已批准）：风控平仓轮应「保留尚未成功提交的待开仓腿」
def test_risk_exit_round_retains_pending_open_legs():
    state = make_state(deferred_open_legs=[leg_a, leg_b])

    run_risk_exit_round(state)

    # ❌ 断言与 spec 逐字对齐 —— 它断言的正是那个错误行为
    assert state.deferred_open_legs == [leg_a, leg_b]
    # 绿色。实现忠实、spec 已批准、用例断言一致，三者自洽。
    # 但这条断言把「风控离场后待开腿复活」固化成了契约。
```

### ✅ 正确示例

```python
# 先做「忠实实现的最坏后果」推演，再写断言：
#   忠实实现 → 待开腿活过风控离场 → 下一轮把刚离场的一对仓位重新开出
#   → 只剩一条腿成交时即为单边裸暴露
# 结论：spec 条款本身是缺陷，须由用户裁决并登记为大偏离。


# 1) 改写被反转的用例：断言方向朝「不回补、不重启」
def test_risk_exit_round_does_not_retain_pending_open_legs():
    state = make_state(deferred_open_legs=[leg_a, leg_b])

    run_risk_exit_round(state)

    assert state.deferred_open_legs == []      # ✅ 随风控离场一并退场


# 2) 补「不复活」回归用例：活着的那条腿不得因重启/回补而重新出现
def test_no_leg_resurrects_after_risk_exit():
    state = make_state(deferred_open_legs=[leg_a, leg_b])
    run_risk_exit_round(state)

    run_round(state)                           # 下一轮调仓

    assert open_legs(state) == []               # ✅ 没有仓位被重新开出
    assert not naked_exposure(state)             # ✅ 不产生单边裸暴露
```

同时补一条元规则：任何反转已批准 SHALL 的改动都必须走用户裁决，**不得静默反转**；
实现方或验证方自行修改 spec 文字后让用例变绿，是比原缺陷更严重的问题。

## 对应失败模式

**(k) 契约断层（contract_gap）**：这里断裂的契约是「spec 与真实意图 / 资金安全之间的
契约」。spec 声称自己表达的是需求方的意图，但这条 SHALL 表达的是一个与意图相反的
行为；对应用例又把 spec 当成事实来源，于是契约的三方（意图 / spec / 用例）中，
spec 与用例站在了一起，与意图脱钩。归到 contract_gap 而不是 coverage_vacuum，是因为
覆盖并不缺失 —— 覆盖很完整，缺的是覆盖对象的正确性：契约的一侧写错了，另一侧忠实
照抄，两侧之间的不一致只有引入第三方基准（资金安全后果）才能暴露。

**置信度说明**：给 0.85。源记录有完整因果链（spec 条款 → 用例断言 → 行为活过风控离场 →
重新开仓 → 单腿裸暴露），并给出了明确的角色级修复（Verifier 独立且有权质疑 spec）；
「用例全绿是反证据」这一反转通用性很强，可直接作为评审清单项落地。未给更高分是因为
源记录只记了 1 次发生，且「用户裁决 + 登记为大偏离」的裁决路径依赖团队流程，属组织
约定而非可自动化的检测，可执行性弱于本包中带检测脚本的条目。

## 改进方向

**短期**：
- 对本轮所有涉及资金安全的 SHALL 逐条做「忠实实现的最坏后果」推演，把结论写进评审记录；
  凡推演结论为「会产生裸暴露 / 重复下单 / 撤单失败」的条款，一律挂起并交用户裁决。
- 复查所有「断言与 spec 逐字对齐」的资金安全用例，尤其是预置条件含止损 / 风控 / 强平的
  那些：这些用例的断言方向必须朝「不回补、不重启」。
- 反转过 SHALL 之后，同步改写原用例，并补一条「不复活」回归用例 —— 缺这条用例时，
  回归会以「旧用例变红」的形式被误判为回归缺陷。

**长期**：
- 确立角色分离：Verifier 独立于 Implementer，并明确拥有质疑 spec 的权限；把「实现 vs
  spec 对齐检查」和「spec vs 意图检查」拆成两个不同的门，后者由前者之外的人执行。
- 在流程上登记 spec 缺陷的处置通道（用户裁决 + 大偏离登记），禁止静默反转已批准的 SHALL。
- 把「绿色用例即反证据」这一认知写进评审清单：当某个 TC 的绿色恰好证明了一个危险行为
  被固化时，绿色本身应被当作待复核信号。
