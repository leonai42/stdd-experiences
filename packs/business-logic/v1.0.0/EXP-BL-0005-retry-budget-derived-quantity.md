## 详细描述

重试的「总覆盖时长」是一个**派生量**：`覆盖时长 = 次数上限 × 有效重试周期`，其中
有效周期 = 间隔 + 单轮自身耗时（不是单纯的 sleep 值 —— 单轮本身要花时间，这部分被
漏掉时实算会系统性偏乐观）。

这个派生量在系统里没有任何一处被写下来：次数上限在主循环入口，节流值在策略配置，
两者相距很远，乘积只存在于读过这两处代码的人的脑子里。

实例：有人提议把重试周期缩到原来的约 1/5，同时把次数上限提到 3 倍。直觉是「更频繁，
而且更持久」——「更频繁」来自周期变小，「更持久」来自次数变多。实算：
`1/5 × 3 = 0.6`，总覆盖时长反而降到基线的 0.6 倍，比改动前更差。该提议未被采纳。

最终采取的方案是把次数上限提到 6 倍（周期不动），得约 1.2 倍基线，即略微提高覆盖时长。

这不是「算错了」，而是**两个旋钮的乘积没有被当成一个东西看**：只讨论被提到的那一个
旋钮时，「更频繁」和「更持久」听起来是两件各自成立的好事，没有任何一步会强迫你去做
乘法。

## 根因链

1. **现象层**：一次「看起来更安全」的重试参数调整，实际把总覆盖时长降到了基线的 0.6 倍。
2. **直接原因**：两个旋钮分居不同位置，且没有任何一处写下它们共同决定的派生量。
3. **为什么直觉会反向**：周期变小与次数变大在语言上分别对应「更频繁」和「更持久」，
   两个词都是正向的；把两者放在一起时，「更频繁 × 更多次」的组合读起来是「更频繁且
   更持久」，而实算方向取决于两个倍率的乘积落在 1 的哪一侧。语言在这里提供了错误的方向感。
4. **本质原因**：系统的真实承诺是一个**复合量**（覆盖时长），但配置面上暴露的是两个
   **分量**，且没有任何一处把复合关系登记下来。分母（有效周期）也不等于看起来的那个
   值 —— 它包含单轮自身耗时，于是即便做了乘法，用 sleep 值代入仍会偏乐观。修法因此
   有两步：把派生量写下来，并且把「有效周期」的定义也写下来。

## 代码示例

### ❌ 错误示例

```python
# 主循环入口：次数上限
MAX_RETRIES = <baseline_retries>          # 提议：提到 3 倍

# 策略配置（另一处文件）：节流值
RETRY_INTERVAL_SEC = <baseline_interval>  # 提议：缩到 1/5

# ❌ 没有任何一处写下派生量。评审时只能看到「周期变小了，更频繁了」，
#    或者「次数变多了，更持久了」—— 两者永远不会在同一个视野里相乘。
#    实算： (1/5) * 3 = 0.6   → 覆盖时长反而降到基线的 0.6 倍
```

### ✅ 正确示例

```python
# 成对旋钮定义在同一处，并写明派生公式
MAX_RETRIES = <final_retries>          # 次数上限（本次由基线提到 6 倍）
RETRY_INTERVAL_SEC = <interval>        # 节流值（两次重试之间的等待）
SINGLE_ROUND_SEC = <round_sec>         # 单轮自身耗时（实测，不是估算）

# 覆盖时长 = 次数上限 × 有效周期；有效周期 = 间隔 + 单轮耗时（不是单纯的 sleep 值）
def retry_coverage_sec() -> float:
    effective_period = RETRY_INTERVAL_SEC + SINGLE_ROUND_SEC
    return MAX_RETRIES * effective_period


# spec 的可测 AND 子句：覆盖时长不低于实测最长故障窗
MEASURED_WORST_FAILURE_WINDOW_SEC = <measured_window>
BASELINE_COVERAGE_SEC = <baseline_coverage>

def test_retry_coverage_covers_worst_failure_window():
    assert retry_coverage_sec() >= MEASURED_WORST_FAILURE_WINDOW_SEC
    assert retry_coverage_sec() >= BASELINE_COVERAGE_SEC   # 不劣于基线
```

用例断言的是**派生关系**（两个配置量算出乘积，再与基线下界比较），不是写死的字面量；
这样任何一侧的旋钮被改动时，用例都会重新算一遍。若断言写成
`assert MAX_RETRIES == 6`，这次改动就会被测到，而下一次以别的组合达成的同等覆盖时长
却会被误判为回归。

## 对应失败模式

**(f) 运行时偏离（runtime_deviation）**：系统的运行时实际行为（重试总覆盖时长 0.6 倍
基线）与 spec / 评审时的意图（「更频繁且更持久」，即覆盖时长增加）不一致。归到
runtime_deviation 而不是 contract_gap，是因为这里两侧没有各持一份互相冲突的契约：
配置面与消费面都忠实工作，偏离发生在**从配置到运行时效果**这一步 —— 两个分量的组合
结果与设计意图相反，且该偏离在静态阅读配置时完全不可见，只有在实算或实测覆盖时长时
才暴露。这也正是本类的典型形态：取值改了，运行时语义跟着变了，但没人算过派生量。

**置信度说明**：给 0.80。源记录含一次反直觉的实算（1/5 × 3 = 0.6 倍基线），把
「直觉方向与实算方向相反」这件事钉得很实，且修复模板具体（成对旋钮同处定义 + spec 写成
可测 AND 子句 + 用例断言派生关系）。未给更高分有两个原因：一是源记录只记了 1 次发生；
二是关键常量（有效周期里的单轮自身耗时、最长故障窗）在源记录中未给出数值，本条的
「覆盖时长必须不低于实测最长故障窗」只能停留在可测子句的形式上，具体阈值仍需使用者
自行实测后填入。

## 改进方向

**短期**：
- 清点所有成对 / 成组的调优旋钮（重试次数 × 间隔、超时 × 轮询次数、批量大小 × 并发度
  等），把它们移到同一处定义，并在注释里写下派生公式。
- 对已发生的取值变更补算派生量，与变更前基线对比，把结论登记进偏离账本 ——
  尤其是那些「看起来是优化」但未做过乘法的改动。
- 把「有效周期 = 间隔 + 单轮自身耗时」这条定义写进代码，并用实测值替换估算值。

**长期**：
- 把「覆盖时长不低于实测最长故障窗」写成 spec 里可测的 AND 子句，让它成为一条回归
  不变量，而不是一句设计意向。
- 用例一律断言派生关系（从配置读分量、算乘积、与下界比较），不写字面量 —— 这样旋钮
  怎么调都能被测到，且不会把合理的新组合误判为回归。
- 形成一条评审纪律：任何重试 / 超时 / 节流参数的改动，评审意见里必须出现派生量的
  新旧对比。没有这个对比的改动不予通过 —— 语言给出的方向感在乘法面前不可靠。
