## 详细描述

一次「把上限抬到新的边界取值」的变更中，test-plan 对某条既有 TC 写下了这样一句：

> 已覆盖；本次取值变化下同样成立。

这句话在评审里几乎不会引起注意，因为它旁边站着一个绿着的用例名 —— 那个用例确实存在、
确实在跑、确实通过。问题在于：它的参数是**旧取值**。新取值这条路径从头到尾没有被执行过
一次，而它恰恰是最需要被执行的那一条：新的上界取值是这一档里最可能被上游（交易所侧）
拒绝的取值，被拒绝之后的行为（上报、回退、拒绝记录）正是这条 TC 声称已经覆盖的行为。

于是「已覆盖」是一句没有任何证据支撑的声明，且它披着一条绿用例的外衣。

## 根因链

1. **现象层**：test-plan 声称某行为在新取值下已覆盖；实际用例参数不含新取值，
   新取值路径零覆盖，却没有任何检查变红。
2. **直接原因**：覆盖声明按行为写，而用例按取值写，两者之间没有一一对应的核对动作。
3. **为什么容易滑过去**：「顺带成立」是一个**弱断言**，它不需要举证就能写下来；
   而核对它需要逐条打开用例看参数 —— 成本高、动作琐碎，评审时天然被跳过。
   更关键的是它的邻接证据（绿用例名）会让读者产生「已经有人验证过」的错觉。
4. **本质原因**：覆盖是关于「取值 × 行为」的二维论断，但声明只用一维（行为）表达。
   只要缺了「取值」这一维，声明就永远无法被证伪 —— 无法证伪的声明在评审中必然滑过。
   所以修法的方向不是「写声明时更谨慎」，而是让声明可核对：声明里必须能读出
   「哪个用例、跑在哪个取值上」。

## 代码示例

### ❌ 错误示例

```python
# 变更：把上限抬到新的边界取值
NEW_BOUND = <new_bound>      # 旧取值：<old_bound>

# test-plan 原文：「上限相关行为已覆盖；本次取值变化下同样成立」

# 既有用例 —— 参数写死旧取值，新取值路径从未执行
def test_over_bound_is_rejected():
    result = submit_order(leverage=<old_bound>)     # ❌ 旧取值：走不到新边界那条分支
    assert result.rejected is False


# 新取值恰好是最可能被上游拒绝的一档，而「被拒绝之后怎么办」这条路
# 在整个测试目录里没有任何一条用例踩到
```

注意：这里**没有**缺少用例数量 —— 缺的是「用例参数含新取值」。所以按用例数或覆盖率
百分比做的检查不会报警：这条用例和以前一样绿。

### ✅ 正确示例

```python
NEW_BOUND = <new_bound>
OLD_BOUND = <old_bound>

# 1) 既有用例保留为，但显式标注它覆盖的是哪个取值
def test_within_old_bound_is_accepted():
    result = submit_order(leverage=OLD_BOUND)
    assert result.rejected is False


# 2) 优先补边界取值的用例 —— 新值放大的正是边界路径
@pytest.mark.parametrize("leverage", [NEW_BOUND])
def test_at_new_bound_rejection_is_reported(leverage):
    result = submit_order(leverage=leverage)
    # ✅ 断言的是「新取值下最可能发生的那件事」：被上游拒绝时会被上报
    assert result.rejected is True
    assert result.rejection_reason is not None


# 3) 反过来：把「同样成立」降级为「未验证」也是合格处置
#    如果本轮不打算补用例，test-plan 里必须写成
#    「新取值下的行为未验证（无对应用例）」，不得写「同样成立」
```

配套的核对动作（本条经验真正的落点）：**凡出现「同样成立」，就去打开那条用例看参数**。
参数含新取值才算覆盖；不含就改写声明或补用例，二者必居其一。

## 对应失败模式

**(j) 覆盖真空（coverage_vacuum）**：有 spec（TC 明确声称已覆盖），但没有测试覆盖
（该取值下零执行）。这正是覆盖真空的定义 —— 文档层的覆盖声明与执行层的覆盖事实脱节，
且脱节不会被任何自动化检查发现，因为覆盖率工具只看「代码行是否被执行」，不看
「这次执行用的是哪个取值」。归到 coverage_vacuum 而不是 contract_gap，是因为这里不存在
两侧契约不一致的问题：用例本身与其参数完全自洽，规范也没有写错；缺的纯粹是那条路径上
的一次真实执行。

**置信度说明**：给 0.85。源记录把失效机制说得很精确（覆盖声明按行为写、用例跑在旧取值
上、新取值恰是最易被上游拒绝的一档），且给了两条可操作处置（补用例 / 降级为「未验证」），
修复模板里「优先给边界取值单独补用例」还能直接落成参数化用例。未给更高分是因为源记录
只记了 1 次发生，且源记录的 `language` 为空 —— 本条目按其语境（交易参数上限变更）判为
Python，若来源项目实际不是 Python，代码示例只能作示意，不能当作原样复用的模板。

## 改进方向

**短期**：
- 检索本轮及历史 test-plan / 报告里所有「同样成立」「顺带覆盖」「本次不改」类措辞，
  逐条打开对应用例核对参数：含新取值的保留，不含的补用例或降级为「未验证」。
- 边界取值（上界 / 下限 / 恰好等于阈值）优先级最高，先补这些；它们是新值真正放大的
  那条路径。
- 在 test-plan 的模板里把声明格式改成「用例名 + 取值」的形式，让声明自带可核对信息。

**长期**：
- 让覆盖声明可证伪：要求每条覆盖声明能指向「哪个用例、跑在哪组参数上」；做不到的
  声明在评审中直接视为未验证。
- 把「取值 × 行为」显式建模：参数化用例的取值集合应由变更引入的新取值驱动，而不是
  沿用旧用例写死的字面量。
- 在 CI 里加一条低成本检查：变更中出现的数值字面量（尤其是配置上限 / 阈值）必须
  在测试参数集合中出现过，否则报警。这条检查不保证语义正确，但能精确拦住本模式。
