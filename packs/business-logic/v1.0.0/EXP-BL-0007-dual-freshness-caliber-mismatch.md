## 详细描述

系统里有两处在判断「这个数据还新不新」，而它们使用完全不同的口径：

- **置信度模型**：按通用时效桶打分 —— 距今 ≤30 天给 0.6，否则给 0.3。这个桶是全局
  常量，对所有数据源一视同仁，不区分数据源本身多久发布一次。
- **业务闸门**：按字段的自然频率判陈旧 —— 月频字段给 40 天，周度字段给 14 天。
  这是业务侧对「这个字段多久会有新值」的正确认识。

对一个自然发布频率是月度的报价源（`<supplier>`），两者的结论相反：置信度模型的 30 天
桶在两次月度发布之间的大部分时间里都判它「旧」（低等级），业务闸门则认为它一直有效
（40 天窗口覆盖得住月度节奏）。

实测表现是：该字段在来源表里显示**低等级**徽章，而报告正文仍然基于它给出方向性断言。
同一份报告里，同一个字段同时是「不可信」和「可用」。

本条记录为集成验证阶段发现、当轮未修复、转入下一轮处置 —— 也就是说，这个不一致在
读者看到的产物里存在过。

## 根因链

1. **现象层**：来源表标低等级，正文用该字段下方向断言；两处说法冲突。
2. **直接原因**：两套新鲜度判据（通用时效桶 / 自然频率窗口）并存，各判各的。
3. **为什么没被发现**：两个判定各自都「对」—— 模型按它声明的通用规则算，闸门按它
   声明的业务规则算。冲突只出现在**同一份产物的两个位置之间**，而没有任何一处负责
   检查这两处是否一致。更隐蔽的是，这类冲突不会抛异常、不会让测试变红，它只让读者
   看到自相矛盾的报告。
4. **本质原因**：同一个概念（这个字段算不算陈旧）有两个事实来源，且二者之间没有
   共同的基准。判据一旦有第二份实现，就必须显式对齐；这里没对齐，于是形成了
   「双事实来源」（dual-source-of-truth）—— 每个来源单独看都自洽，合起来才矛盾。

## 代码示例

### ❌ 错误示例

```python
# 置信度模型：通用时效桶，全局常量，不感知数据源的发布频率
def score_freshness(age_days: int) -> float:
    if age_days <= 30:          # ❌ 对所有字段一视同仁
        return 0.6
    return 0.3


# 业务闸门：另起一套阈值，按字段自然频率判陈旧
NATURAL_FREQ_DAYS = {
    "monthly": 40,              # 月频字段
    "weekly": 14,               # 周度字段
}

def is_stale(field: str, age_days: int) -> bool:
    return age_days > NATURAL_FREQ_DAYS[FREQ_OF[field]]


# 结果：月频字段在第 31~40 天之间
#   来源表：score_freshness 给 0.3 → 显示低等级（不可信）
#   正文：  is_stale 判 False    → 照常用于方向断言（可用）
# 两个判定各自自洽，冲突无人检查。
```

### ✅ 正确示例

```python
# 单一来源：自然频率表由两处共用
NATURAL_FREQ_DAYS = {"monthly": 40, "weekly": 14}
FREQUENCY_BUCKET = {"monthly": 40 * 1.0, "weekly": 14 * 1.0}


def score_freshness(field: str, age_days: int) -> float:
    window = FREQUENCY_BUCKET[FREQ_OF[field]]     # ✅ 引入自然频率，与闸门同源
    if age_days <= window:
        return 0.6
    return 0.3


def is_stale(field: str, age_days: int) -> bool:
    return age_days > NATURAL_FREQ_DAYS[FREQ_OF[field]]


# ✅ 一致性断言：同一字段、同一年龄，两处不得给出矛盾结论
def test_freshness_verdicts_agree_across_both_calibers():
    for field in ALL_FIELDS:
        for age in range(0, 120):
            model_ok = score_freshness(field, age) >= LOW_GRADE_THRESHOLD
            gate_ok = not is_stale(field, age)
            assert model_ok == gate_ok, (field, age, model_ok, gate_ok)


# 退路（口径无法统一时）：在闸门处把低置信度输入一并降级为 stale
def is_stale_conservative(field: str, age_days: int) -> bool:
    return is_stale(field, age_days) or score_freshness(field, age_days) < LOW_GRADE_THRESHOLD
    # 宁可中性，不可误断言
```

一致性断言是这条经验最好落地的一步：它不要求先决定「哪套口径对」，只要求「两处不得
互相矛盾」，因此在口径优先级尚未与用户确认之前就能先加上。

## 对应失败模式

**(k) 契约断层（contract_gap）**：新鲜度这个概念的提供方有两个（置信度模型 / 业务
闸门），它们对外都代表「该字段是否可信」，但各自的契约不同（通用时效桶 vs 自然频率
窗口），消费方（报告渲染层与正文撰写逻辑）却分别采信了不同的一个。归到 contract_gap
而不是 cross_system_mismatch，是因为这不是两个独立系统之间的偶发不一致，而是**同一
系统内同一概念有两份契约实现**、且二者之间缺少对齐义务 —— 典型特征是每一份单独看
都完全正确，冲突只在合并产物时出现，且不会触发任何错误或告警。

**置信度说明**：给 0.75。源记录把两套口径的具体阈值都写明了（≤30 天 0.6 / 否则 0.3
对 月频 40 天 / 周度 14 天），可以直接据此写出一致性断言，这一点使条目可落地；
「双口径无共同口径」也确属报告类系统的通病，通用性好。未给更高分有三个原因：一是
源记录只记了 1 次发生；二是本条的核心处置被源记录明确标为需要先与用户确认口径优先级
（改动影响全量字段等级），落地上多一道外部依赖；三是源记录未记录修复后的验证结果
（当轮未修复，转入下一轮），因此无法确认该处置真的消除了不一致。

## 改进方向

**短期**：
- 先加一致性断言（不改变任何阈值）：对全量字段扫描年龄区间，断言两处新鲜度判定
  不出现矛盾。这一步不需要先裁决口径优先级，可立即执行。
- 复查当前对外产物：找出所有「低等级输入支撑强断言」的位置，逐条确认是补口径说明、
  还是把断言强度降下来。
- 与用户确认口径优先级后再动阈值 —— 改动会影响全量字段的等级，属于跨字段影响面的
  改动，不宜作为局部修复推进。

**长期**：
- 消灭双事实来源：自然频率表只保留一份，置信度模型与业务闸门都从它派生阈值。
- 确立组合规则：当同一概念存在多个判据且暂时无法统一时，取**更保守**的一侧
  （宁可中性，不可误断言），并把这条规则写进实现而不是留给调用方。
- 在渲染层加一条产物级检查：同一字段在报告的不同位置若承载相反的可用性结论，
  应在生成阶段就报警 —— 这类矛盾对读者而言是硬伤，但对测试而言完全不可见。
