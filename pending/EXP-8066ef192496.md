## 正文

### 现象

本 change 的 CP-LGR-1/2 动作是 `python -m ledger backfill ... --intensity 震荡 --root .`。
ADJ-011 已把「回填落库用 `基差震荡` 全词」登记为已解决，但只改了 code spec 的期望值文本，
**agent spec 里这条命令的实参值没改**。后果：

1. 手工回填后 `knowledge_data<project>/<module>` 的 `intensity_label` = `基差震荡`；
2. 跑 `stdd verify run`（21:36:40），CP-LGR-1/2 报 **aligned**；
3. 回读同一文件，`intensity_label` 退回 `震荡`。

闸门全绿，生产数据被改坏。这是**验证器对生产目录有写权限**与**契约订正只改了一半**叠加的结果。

### 为什么会漏

- 校验条件只有 `exit_code` / `stdout_contains` / `stderr_contains` / `file_exists`，
  没有任何一条回读「被写文件的内容是否等于意图值」；
- `--root .` 让验证跑在真实仓库上，CP 的语义是「演示这条命令可用」，
  但副作用是「真实落账」—— 验证器不区分两者；
- 期望值改了、实参值没改，二者不一致不会报错：命令照常成功，写的却是旧值。

### 怎么防

1. **订正契约要盯实参值**：改期望值时，同步 grep 该 capability 的 agent spec 里有没有把同一个值写死在 action 上。
2. **复跑验证后回读被写文件**：以「数据是否被改写」当判据，不以「CP 是否绿」当判据。
3. **加一致性用例**：断言 agent spec 的 CP 实参值 == code spec 的期望值
   （本仓落点 `tests<project>/<module>`）。
4. **长远的**：写生产目录的 CP 要么跑在只读根/沙箱里，要么必须幂等且值可核。
